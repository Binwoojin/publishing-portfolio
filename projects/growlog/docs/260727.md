# 📅 GrowLog 개발일지 — 2026.07.27

## 1. 오늘의 개발 목표

오늘은 성장 기록에 이미지를 첨부할 수 있도록 구현 중인 Media 기능에서 발생한 AWS S3 연동 문제를 해결하는 것을 목표로 하였다.

기존에는 이미지 파일을 S3에 업로드하고 Media 테이블에 저장하는 구조를 구현하고 있었지만, 업로드된 이미지를 화면에서 조회하기 위한 URL 생성 부분과 AWS 인증 정보 설정에서 오류가 발생하였다.

오늘 해결한 주요 작업은 다음과 같다.

```text
S3 Presigned URL 생성 기능 구현
→ S3FileStorageService 보완
→ MediaService의 이미지 URL 처리 방식 점검
→ S3Presigner Bean 등록
→ AWS CredentialsProvider 오류 해결
→ 이미지 업로드 및 조회 구조 정리
```

## 2. Media 이미지 저장 구조 점검

GrowLog의 Media 기능은 성장 기록 하나에 여러 개의 이미지 또는 미디어가 연결될 수 있도록 구성하고 있다.

이미지 등록 과정은 다음과 같이 설계하였다.

```text
사용자가 성장 기록 작성
→ 이미지 파일 선택
→ 서버에서 이미지 파일 검증
→ AWS S3에 이미지 업로드
→ S3 Object Key 생성
→ Media Entity 생성
→ Media 테이블에 저장
```

이미지를 S3에 업로드한 뒤 DB에는 전체 접근 URL을 직접 저장하기보다 이미지의 위치를 나타내는 `objectKey`를 저장하는 방향으로 구성하였다.

예시는 다음과 같다.

```text
growth-records/15/550e8400-image.jpg
```

이를 기반으로 이미지가 필요한 시점에 Presigned URL을 생성하여 화면에 전달하도록 하였다.

---

## 3. Presigned URL 사용 이유

S3 버킷을 공개 상태로 설정하면 객체 URL만 알고 있는 사람은 누구나 이미지에 접근할 수 있다.

GrowLog의 성장 기록 이미지는 회원 개인 데이터이므로 S3 버킷을 비공개로 유지하고, 일정 시간 동안만 접근할 수 있는 Presigned URL을 사용하는 방향이 적절하다고 판단하였다.

전체 조회 흐름은 다음과 같다.

```text
DB에 S3 Object Key 저장
→ 이미지 조회 요청
→ 서버에서 Presigned URL 생성
→ 제한된 시간 동안 이미지 접근 허용
→ JSP 또는 클라이언트에 URL 전달
```

Presigned URL을 사용하면 S3 객체를 공개하지 않고도 사용자가 자신의 이미지를 조회할 수 있다.

## 4. S3FileStorageService의 Presigned URL 생성 기능 구현

`S3FileStorageService`에 비어 있던 `createPresignedUrl()` 메서드를 구현하였다.

```java
public String createPresignedUrl(String objectKey) {

    // 조회할 S3 객체의 버킷명과 객체 키를 설정한다.
    GetObjectRequest getObjectRequest =
            GetObjectRequest.builder()
                    .bucket(bucketName)
                    .key(objectKey)
                    .build();

    // Presigned URL의 유효 시간과 실제 S3 조회 요청을 설정한다.
    GetObjectPresignRequest presignRequest =
            GetObjectPresignRequest.builder()
                    .signatureDuration(
                            Duration.ofMinutes(10)
                    )
                    .getObjectRequest(getObjectRequest)
                    .build();

    // S3Presigner를 이용하여 서명된 임시 접근 URL을 생성한다.
    PresignedGetObjectRequest presignedRequest =
            s3Presigner.presignGetObject(
                    presignRequest
            );

    return presignedRequest.url().toString();
}
```

메서드는 다음 순서로 동작한다.

```text
objectKey 전달
→ GetObjectRequest 생성
→ URL 유효 시간 지정
→ S3Presigner로 서명
→ Presigned URL 문자열 반환
```

## 5. Presigned URL 유효 시간 설정

Presigned URL은 영구적으로 사용할 수 있는 URL이 아니라 설정한 시간 동안만 사용할 수 있다.

오늘 구현한 코드에서는 다음과 같이 10분의 유효 시간을 적용하였다.

```java
.signatureDuration(
        Duration.ofMinutes(10)
)
```

화면을 새로 요청하면 서버에서 새로운 Presigned URL을 발급할 수 있으므로 DB에는 만료되는 URL을 저장하지 않도록 하였다.

```text
DB 저장 대상
→ S3 Object Key

DB에 저장하지 않는 값
→ Presigned URL
```

Presigned URL은 시간이 지나면 만료되기 때문에 DB에 직접 저장하면 이후 사용할 수 없는 주소가 남게 된다.

## 6. S3FileStorageService 의존성 구성

Presigned URL 생성을 위해 기존 `S3Client`와 함께 `S3Presigner`를 주입받도록 구성하였다.

```java
@Service
@RequiredArgsConstructor
public class S3FileStorageService {

    private final S3Client s3Client;
    private final S3Presigner s3Presigner;

    @Value("${cloud.aws.s3.bucket}")
    private String bucketName;
}
```

각 객체의 역할은 다음과 같다.

| 객체            | 역할                      |
| ------------- | ----------------------- |
| `S3Client`    | 파일 업로드 및 삭제 등 S3 객체 관리  |
| `S3Presigner` | 비공개 객체에 접근할 임시 URL 생성   |
| `bucketName`  | 이미지를 저장하거나 조회할 S3 버킷 이름 |

업로드와 조회 URL 생성을 하나의 Client로 처리하지 않고 역할에 맞게 구분하였다.

## 7. MediaService의 이미지 등록 로직 점검

이미지를 업로드하고 Media Entity를 저장하는 `uploadAndSaveImageMedia()` 메서드의 구조를 점검하였다.

```java
@Transactional
public Media uploadAndSaveImageMedia(
        GrowthRecord growthRecord,
        MultipartFile imageFile,
        Long memberNo,
        Integer sortOrder
) {
    validateGrowthRecord(growthRecord);

    if (memberNo == null) {
        throw new IllegalArgumentException(
                "회원 번호가 필요합니다."
        );
    }

    // 이미지 파일을 S3에 업로드하고
    // DB에 저장할 Object Key를 반환받는다.
    String objectKey =
            s3FileStorageService.uploadImage(
                    imageFile,
                    memberNo
            );

    Media media =
            Media.builder()
                    .growthRecord(growthRecord)
                    .mediaType(MediaType.IMAGE)
                    .mediaUrl(objectKey)
                    .sortOrder(sortOrder)
                    .build();

    return mediaRepository.save(media);
}
```

Media 등록 과정에서는 Presigned URL이 아니라 S3의 `objectKey`를 저장하도록 하였다.

## 8. MediaService에서 Presigned URL을 저장하지 않는 이유

이미지를 업로드한 직후 Presigned URL을 생성하여 `mediaUrl` 컬럼에 저장하는 방식도 생각할 수 있지만, 이 방식에는 문제가 있다.

```text
Presigned URL 생성
→ DB에 URL 저장
→ 설정 시간이 지나면 URL 만료
→ DB에는 접근할 수 없는 URL이 남음
```

따라서 Media 테이블에는 다음과 같은 값만 저장하는 것이 적절하다.

```text
growth-records/{memberNo}/{uuid}-{fileName}
```

이미지를 실제 화면에 출력할 때만 `createPresignedUrl()`을 호출하도록 역할을 분리하였다.

```text
이미지 등록
→ Object Key 저장

이미지 조회
→ Object Key로 Presigned URL 생성
```

## 9. Media 조회 시 URL 변환 구조

Media Entity에는 S3 Object Key가 저장되므로 JSP에 Entity를 그대로 전달하면 이미지가 표시되지 않는다.

따라서 화면에 전달할 DTO에서 Object Key를 Presigned URL로 변환하는 구조를 사용할 수 있다.

```java
String imageUrl =
        s3FileStorageService.createPresignedUrl(
                media.getMediaUrl()
        );
```

예를 들어 Media 응답 DTO를 사용할 경우 다음과 같이 구성할 수 있다.

```java
public MediaResponse toResponse(Media media) {

    String accessUrl = null;

    if (media.getMediaType() == MediaType.IMAGE) {
        accessUrl =
                s3FileStorageService
                        .createPresignedUrl(
                                media.getMediaUrl()
                        );
    }

    return MediaResponse.builder()
            .mediaNum(media.getMediaNum())
            .mediaType(media.getMediaType())
            .mediaUrl(accessUrl)
            .sortOrder(media.getSortOrder())
            .build();
}
```

이를 통해 DB 저장 구조와 화면 출력 구조를 분리할 수 있다.

## 10. S3Config에 S3Presigner Bean 등록

`S3FileStorageService`에서 `S3Presigner`를 주입받을 수 있도록 `S3Config`에 Bean을 등록하였다.

```java
@Configuration
public class S3Config {

    @Bean
    public S3Presigner s3Presigner(
            AwsCredentialsProvider credentialsProvider
    ) {
        return S3Presigner.builder()
                .region(Region.AP_NORTHEAST_2)
                .credentialsProvider(
                        credentialsProvider
                )
                .build();
    }
}
```

AWS 서울 리전을 사용하고 있으므로 다음 Region을 설정하였다.

```java
Region.AP_NORTHEAST_2
```

S3 업로드에 사용하는 `S3Client`와 Presigned URL 생성에 사용하는 `S3Presigner`가 동일한 Region 및 인증 정보를 사용하도록 구성하였다.

## 11. credentialsProvider 오류 해결

초기에는 `s3Presigner()` 메서드 안에서 다음과 같이 `credentialsProvider()`를 직접 호출하였다.

```java
@Bean
public S3Presigner s3Presigner() {
    return S3Presigner.builder()
            .region(Region.AP_NORTHEAST_2)
            .credentialsProvider(
                    credentialsProvider()
            )
            .build();
}
```

하지만 `credentialsProvider()` 메서드가 존재하지 않거나 반환 타입이 맞지 않아 오류가 발생하였다.

이를 해결하기 위해 AWS SDK에서 제공하는 `AwsCredentialsProvider` Bean을 별도로 등록하였다.

```java
@Bean
public AwsCredentialsProvider credentialsProvider(
        @Value("${cloud.aws.credentials.access-key}")
        String accessKey,

        @Value("${cloud.aws.credentials.secret-key}")
        String secretKey
) {
    AwsBasicCredentials credentials =
            AwsBasicCredentials.create(
                    accessKey,
                    secretKey
            );

    return StaticCredentialsProvider.create(
            credentials
    );
}
```

이후 필요한 Bean에서 메서드를 직접 호출하기보다 Spring 의존성 주입을 사용하도록 수정하였다.

```java
@Bean
public S3Presigner s3Presigner(
        AwsCredentialsProvider credentialsProvider
) {
    return S3Presigner.builder()
            .region(Region.AP_NORTHEAST_2)
            .credentialsProvider(
                    credentialsProvider
            )
            .build();
}
```

## 12. S3Client 인증 정보 통일

S3 업로드에 사용하는 `S3Client`도 동일한 `AwsCredentialsProvider`를 주입받도록 구성하였다.

```java
@Bean
public S3Client s3Client(
        AwsCredentialsProvider credentialsProvider
) {
    return S3Client.builder()
            .region(Region.AP_NORTHEAST_2)
            .credentialsProvider(
                    credentialsProvider
            )
            .build();
}
```

최종 Bean 관계는 다음과 같다.

```text
AwsCredentialsProvider
├─ S3Client
└─ S3Presigner
```

동일한 인증 정보 Bean을 재사용하여 업로드와 URL 생성 설정의 중복을 줄였다.

## 13. AWS 설정값 분리

AWS Access Key와 Secret Key를 Java 코드에 직접 작성하지 않고 환경 설정 파일에서 주입받도록 구성하였다.

```yaml
cloud:
  aws:
    credentials:
      access-key: ${AWS_ACCESS_KEY}
      secret-key: ${AWS_SECRET_KEY}

    s3:
      bucket: ${AWS_S3_BUCKET}
```

환경 변수 또는 별도의 비공개 설정 파일을 통해 실제 값을 관리하도록 하였다.

GitHub에 업로드되는 설정 파일에 실제 AWS 인증 정보가 포함되지 않도록 주의해야 한다.

```text
코드 및 GitHub
→ 환경 변수 이름만 기록

로컬 및 배포 환경
→ 실제 AWS 인증 정보 설정
```

## 15. Presigned URL 적용 시 보안 고려사항

Presigned URL은 URL을 알고 있는 동안에는 별도의 AWS 인증 없이 객체에 접근할 수 있으므로 필요한 시간보다 지나치게 길게 설정하지 않는 것이 좋다.

현재는 테스트와 화면 조회를 고려하여 10분으로 설정하였다.

```java
Duration.ofMinutes(10)
```

또한 Presigned URL을 생성하기 전에 현재 로그인한 회원이 해당 성장 기록과 Media를 조회할 권한이 있는지도 확인해야 한다.

```text
로그인 회원 확인
→ 성장 기록 작성자 확인
→ Media 소유 관계 확인
→ Presigned URL 생성
```

Presigned URL을 사용한다는 이유만으로 애플리케이션의 회원 권한 검증을 생략해서는 안 된다.

## 16. 오늘 발생한 주요 문제와 해결 결과

오늘 개발 과정에서는 다음 세 가지 핵심 문제를 해결하였다.

### 1. `createPresignedUrl()` 미구현

```text
문제
→ 업로드된 S3 이미지를 조회할 URL을 생성할 수 없음

해결
→ GetObjectPresignRequest와 S3Presigner를 사용하여 구현
```

### 2. MediaService의 URL 저장 방식 혼선

```text
문제
→ Object Key와 Presigned URL 중 어떤 값을 DB에 저장해야 하는지 불명확

해결
→ DB에는 Object Key만 저장
→ 조회 시 Presigned URL을 동적으로 생성
```

### 3. S3Presigner의 CredentialsProvider 오류

```text
문제
→ credentialsProvider() 메서드 또는 Bean 구성 오류

해결
→ AwsCredentialsProvider Bean 별도 등록
→ S3Client와 S3Presigner에 의존성 주입
```

세 문제를 해결하면서 S3 이미지 업로드 및 조회를 위한 기반 구조를 안정적으로 정리하였다.

## 20. 오늘 배운 점

* 비공개 S3 객체를 화면에 표시하려면 Presigned URL을 사용할 수 있다.
* Presigned URL은 만료되기 때문에 DB에 저장하는 값으로 적합하지 않다.
* Media 테이블에는 S3 Object Key를 저장하고 조회 시 URL을 생성하는 것이 좋다.
* `S3Client`는 객체 업로드와 삭제를 담당하고, `S3Presigner`는 임시 접근 URL 생성을 담당한다.
* 여러 AWS Client가 같은 인증 정보를 사용할 때는 `AwsCredentialsProvider`를 공통 Bean으로 분리할 수 있다.
* Spring Bean 메서드를 직접 호출하기보다 메서드 파라미터를 통한 의존성 주입을 사용하면 구성이 명확해진다.
* AWS Access Key와 Secret Key는 코드나 GitHub 저장소에 직접 작성해서는 안 된다.
* Presigned URL을 생성하기 전에도 애플리케이션에서 회원의 데이터 접근 권한을 검증해야 한다.
* 이미지 업로드와 이미지 조회는 서로 다른 처리 흐름으로 나누어 설계하는 것이 유지보수에 유리하다.

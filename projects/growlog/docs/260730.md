## 1. Spring Security 로그인 기능 적용

기존 프로젝트에서는 `HomeController`에서 이메일과 비밀번호를 직접 검사한 뒤 `HttpSession`에 회원 정보를 저장하는 방식으로 로그인 기능을 처리했다.

오늘은 해당 구조를 Spring Security 기반 인증 방식으로 전환했다.

### 의존성 변경

기존에는 비밀번호 암호화 기능만 제공하는 `spring-security-crypto`를 사용하고 있었다.

Spring Security의 인증과 인가 기능 전체를 사용하기 위해 다음 의존성을 추가했다.

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>
```

## 2. `SecurityFilterChain` 구성

`SecurityConfig`를 추가하여 URL별 접근 권한과 로그인 및 로그아웃 처리 방식을 설정했다.

```java
@Bean
public SecurityFilterChain securityFilterChain(
        HttpSecurity http
) throws Exception {

    http.authorizeHttpRequests(authorize -> authorize
                    .requestMatchers(
                            "/goal/**",
                            "/record/**",
                            "/home",
                            "/timeline",
                            "/mypage/**",
                            "/api/member/check-nickname-update"
                    )
                    .authenticated()
                    .anyRequest()
                    .permitAll()
            )
            .formLogin(form -> form
                    .loginPage("/login")
                    .loginProcessingUrl("/login")
                    .usernameParameter("email")
                    .passwordParameter("password")
                    .successHandler(loginSuccessHandler)
                    .failureUrl("/login?error")
                    .permitAll()
            )
            .logout(logout -> logout
                    .logoutUrl("/logout")
                    .logoutSuccessUrl("/logout-complete")
                    .invalidateHttpSession(true)
                    .clearAuthentication(true)
                    .permitAll()
            );

    return http.build();
}
```

### 주요 설정

* `/goal/**`, `/record/**`, `/home`, `/timeline`, `/mypage/**`는 로그인 사용자만 접근할 수 있도록 설정
* 로그인 화면은 기존 `/login` JSP 사용
* `POST /login` 요청은 Controller가 아닌 Spring Security 필터가 처리
* 로그인 식별자로 이메일 사용
* 인증 실패 시 `/login?error`로 이동
* 로그아웃 시 HTTP 세션과 Security 인증 정보를 함께 제거
* 로그아웃 완료 후 `/logout-complete`로 이동

## 3. DB 회원 조회를 위한 `UserDetailsService` 구현

Spring Security가 로그인 요청을 처리할 때 이메일을 기준으로 회원 정보를 조회할 수 있도록 `CustomUserDetailsService`를 구현했다.

```java
@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class CustomUserDetailsService
        implements UserDetailsService {

    private final MemberRepository memberRepository;

    @Override
    public UserDetails loadUserByUsername(
            String email
    ) throws UsernameNotFoundException {

        Member member = memberRepository
                .findByEmail(email)
                .orElseThrow(() ->
                        new UsernameNotFoundException(
                                "회원 정보를 찾을 수 없습니다."
                        )
                );

        return new LoginMemberPrincipal(member);
    }
}
```

### 인증 처리 흐름

```text
사용자가 로그인 폼에 이메일과 비밀번호 입력
→ Spring Security가 loadUserByUsername() 호출
→ 이메일을 기준으로 Member 조회
→ 조회한 회원을 LoginMemberPrincipal로 변환
→ PasswordEncoder를 사용해 비밀번호 비교
→ 인증 성공 시 Security Context에 인증 정보 저장
```

## 4. 인증 사용자 객체 구현

JPA의 `Member` Entity를 인증 객체로 직접 사용하지 않도록 `LoginMemberPrincipal`을 추가했다.

```java
@Getter
public class LoginMemberPrincipal
        implements UserDetails {

    private final Long memberNo;
    private final String email;
    private final String password;
    private final String nickname;

    public LoginMemberPrincipal(Member member) {
        this.memberNo = member.getMemberNo();
        this.email = member.getEmail();
        this.password = member.getPassword();
        this.nickname = member.getNickname();
    }

    @Override
    public String getUsername() {
        return email;
    }

    @Override
    public Collection<? extends GrantedAuthority>
    getAuthorities() {

        return List.of(
                new SimpleGrantedAuthority(
                        "ROLE_USER"
                )
        );
    }
}
```

### 적용 이유

* 인증 객체와 영속성 Entity의 책임 분리
* 인증에 필요한 최소 정보만 Security Context에 저장
* 회원 번호와 닉네임을 Controller 및 화면에서 활용 가능
* 향후 관리자 권한 등 역할 기반 인가 기능 확장 가능

현재 일반 회원에게는 기본적으로 `ROLE_USER` 권한을 부여했다.

## 5. 기존 세션 로그인과의 임시 호환 처리

기존 Controller 일부는 다음 방식으로 로그인 회원을 조회하고 있었다.

```java
Member loginMember =
        (Member) session.getAttribute(
                "loginMember"
        );
```

Spring Security로 인증 구조를 한 번에 변경하면 기존 Controller가 로그인 회원을 찾지 못하는 문제가 발생할 수 있다.

이를 방지하기 위해 `LoginSuccessHandler`를 구현했다.

```java
@Component
@RequiredArgsConstructor
public class LoginSuccessHandler
        implements AuthenticationSuccessHandler {

    private final MemberService memberService;

    @Override
    public void onAuthenticationSuccess(
            HttpServletRequest request,
            HttpServletResponse response,
            Authentication authentication
    ) throws IOException {

        LoginMemberPrincipal principal =
                (LoginMemberPrincipal)
                        authentication.getPrincipal();

        Member loginMember =
                memberService.findById(
                        principal.getMemberNo()
                );

        request.getSession()
                .setAttribute(
                        "loginMember",
                        loginMember
                );

        response.sendRedirect(
                request.getContextPath()
                        + "/home"
        );
    }
}
```

### 처리 결과

* Spring Security 인증 정보는 `SecurityContext`에 저장
* 기존 Controller와의 호환을 위해 `loginMember`도 세션에 임시 저장
* 로그인 성공 후 `/home`으로 이동

해당 로직은 모든 Controller가 `@AuthenticationPrincipal` 방식으로 전환될 때까지 사용하는 임시 호환 처리이다.

## 7. 로그인 및 로그아웃 흐름 개선

기존 `HomeController`가 직접 처리하던 `POST /login` 로직을 제거했다.

이제 로그인 요청은 Spring Security 인증 필터가 처리한다.

### 루트 경로 처리

```java
@GetMapping("/")
public String root(HttpSession session) {

    if (
        session.getAttribute(
                "loginMember"
        ) != null
    ) {
        return "redirect:/home";
    }

    return "redirect:/login";
}
```

현재는 기존 세션 호환 로직이 남아 있어 세션을 기준으로 분기하지만, 추후 Security 인증 정보 기반으로 변경할 예정이다.

### 로그인 실패 메시지

Spring Security가 로그인에 실패하면 `/login?error`로 이동하도록 설정했다.

JSP에서는 `error` 파라미터가 있을 때 공통 오류 메시지를 표시한다.

```jsp
<input
    type="hidden"
    id="loginErrorMessage"
    value="${param.error != null
        ? '이메일 또는 비밀번호가 올바르지 않습니다.'
        : ''}"
>
```

이메일 존재 여부와 비밀번호 오류를 구분하지 않고 동일한 메시지를 표시하여 가입된 이메일을 추측하기 어렵도록 처리했다.

### 로그아웃 처리

기존 Controller의 세션 무효화 코드를 제거하고 Spring Security가 로그아웃을 처리하도록 변경했다.

```text
HTTP 세션 무효화
→ Security Context 인증 정보 제거
→ 로그아웃 완료 페이지 이동
```

## 8. 실제 데이터 기반 성장 타임라인 구현

기존 정적 예시 데이터로 구성된 타임라인을 로그인 회원의 실제 목표와 성장 기록으로 구성할 수 있도록 백엔드 로직을 구현했다.

### `TimelineItem` DTO 추가

목표와 성장 기록은 서로 다른 Entity이지만 타임라인에서는 동일한 카드 구조로 표시해야 한다.

화면에서 필요한 공통 정보를 `TimelineItem` DTO로 통합했다.

```java
@Getter
@AllArgsConstructor
public class TimelineItem {

    private String type;
    private Long itemNum;
    private String title;
    private String content;
    private LocalDateTime createdAt;
    private String detailUrl;
}
```

### 필드 구성

| 필드          | 설명                 |
| ----------- | ------------------ |
| `type`      | `GOAL` 또는 `RECORD` |
| `itemNum`   | 목표 번호 또는 성장 기록 번호  |
| `title`     | 타임라인에 표시할 제목       |
| `content`   | 타임라인에 표시할 내용       |
| `createdAt` | 생성 시간 및 정렬 기준      |
| `detailUrl` | 항목 클릭 시 이동할 주소     |

## 9. 목표와 성장 기록 통합 서비스 구현

`TimelineService`에서 선택한 월의 목표와 성장 기록을 조회한 뒤 하나의 목록으로 합치도록 구현했다.

```java
public List<TimelineItem> getTimeline(
        Long memberNo,
        YearMonth yearMonth
) {
    List<TimelineItem> timelineItems =
            new ArrayList<>();

    List<Goal> goals =
            goalService
                    .findGoalsByMemberAndMonth(
                            memberNo,
                            yearMonth
                    );

    for (Goal goal : goals) {
        timelineItems.add(
                new TimelineItem(
                        "GOAL",
                        goal.getGoalNum(),
                        goal.getGoalTitle(),
                        goal.getGoalContent(),
                        goal.getCreatedAt(),
                        "/goal/list?openGoal="
                                + goal.getGoalNum()
                )
        );
    }

    List<GrowthRecord> records =
            growthRecordService
                    .findRecordsByMemberAndMonth(
                            memberNo,
                            yearMonth
                    );

    for (GrowthRecord record : records) {
        timelineItems.add(
                new TimelineItem(
                        "RECORD",
                        record.getRecordNum(),
                        record.getTitle(),
                        record.getContent(),
                        record.getCreatedAt(),
                        "/record/"
                                + record.getRecordNum()
                )
        );
    }

    timelineItems.sort(
            Comparator.comparing(
                    TimelineItem::getCreatedAt
            ).reversed()
    );

    return timelineItems;
}
```

### 처리 과정

```text
로그인 회원의 선택 월 목표 조회
→ 목표를 TimelineItem으로 변환
→ 로그인 회원의 선택 월 성장 기록 조회
→ 성장 기록을 TimelineItem으로 변환
→ 두 목록을 하나로 병합
→ 생성 시간 기준 최신순 정렬
```

### 상세 페이지 이동 경로

목표는 별도의 상세 페이지가 없으므로 목표 목록으로 이동한 뒤 특정 목표 모달을 열 수 있도록 다음 주소를 사용했다.

```text
/goal/list?openGoal={goalNum}
```

성장 기록은 기존 상세 페이지로 이동한다.

```text
/record/{recordNum}
```

## 10. 월별 타임라인 조회 기능 구현

`PageController`에서 연도와 월을 쿼리 파라미터로 전달받아 해당 기간의 타임라인 데이터를 조회하도록 구현했다.

```text
/timeline?year=2026&month=7
```

### 기본 동작

* `year`, `month`가 없으면 현재 월 조회
* 올바르지 않은 값이 전달되면 현재 월 사용
* 현재보다 미래인 월을 요청하면 현재 월로 제한
* 이전 달과 다음 달 이동 정보 계산
* 현재 월에서는 다음 달 이동 제한

```java
YearMonth currentMonth =
        YearMonth.now();

try {
    selectedMonth =
            year != null
            && month != null
                    ? YearMonth.of(
                            year,
                            month
                    )
                    : currentMonth;

} catch (RuntimeException e) {
    selectedMonth = currentMonth;
}

if (selectedMonth.isAfter(currentMonth)) {
    selectedMonth = currentMonth;
}
```

### 화면에 전달하는 데이터

* 통합 타임라인 항목
* 선택한 월의 성장 기록 개수
* 선택한 월의 목표 개수
* 현재 연속 기록 일수
* 선택한 연도와 월
* 이전 달과 다음 달
* 현재 월 선택 여부

```java
model.addAttribute(
        "timelineItems",
        timelineItems
);

model.addAttribute(
        "monthlyRecordCount",
        monthlyRecordCount
);

model.addAttribute(
        "monthlyGoalCount",
        monthlyGoalCount
);

model.addAttribute(
        "currentStreak",
        attendanceSummary
                .getCurrentStreak()
);
```

## 11. 월별 데이터 조회 Repository 추가

선택한 월의 데이터만 조회할 수 있도록 목표와 성장 기록 Repository에 기간 조회 메서드를 추가했다.

조회 기간은 시작 시각 이상, 다음 달 시작 시각 미만으로 계산한다.

```text
2026-07-01 00:00:00 이상
2026-08-01 00:00:00 미만
```

### 목표 조회

```java
List<Goal>
findByMemberMemberNoAndCreatedAtGreaterThanEqualAndCreatedAtLessThanOrderByCreatedAtDesc(
        Long memberNo,
        LocalDateTime startDateTime,
        LocalDateTime endDateTime
);
```

### 목표 개수 조회

```java
long
countByMemberMemberNoAndCreatedAtGreaterThanEqualAndCreatedAtLessThan(
        Long memberNo,
        LocalDateTime startDateTime,
        LocalDateTime endDateTime
);
```

### 성장 기록 조회

```java
List<GrowthRecord>
findByMemberMemberNoAndCreatedAtGreaterThanEqualAndCreatedAtLessThanOrderByCreatedAtDesc(
        Long memberNo,
        LocalDateTime startDateTime,
        LocalDateTime endDateTime
);
```

### 개선 결과

* 로그인 회원의 데이터만 조회
* 선택한 월에 생성된 데이터만 조회
* 월말 날짜를 직접 계산하지 않고 다음 달 시작 시각을 종료 조건으로 사용
* 시간 정보가 포함된 `createdAt` 데이터를 안전하게 조회

## 13. 비밀번호 변경 로직 오류 수정

회원 비밀번호 변경 과정에서 현재 비밀번호를 가져와야 하는 부분에 신규 비밀번호를 잘못 사용하고 있었다.

### 수정 전

```java
String currentPassword =
        request.getCurrentPassword() == null
                ? ""
                : request.getNewPassword();
```

### 수정 후

```java
String currentPassword =
        request.getCurrentPassword() == null
                ? ""
                : request.getCurrentPassword();
```

### 원인

현재 비밀번호를 검증하기 위한 변수에 `getNewPassword()` 값을 대입하고 있었다.

이 때문에 사용자가 입력한 현재 비밀번호와 DB에 저장된 암호화 비밀번호를 정상적으로 비교할 수 없었다.

### 결과

사용자가 입력한 현재 비밀번호와 DB에 저장된 암호화 비밀번호를 정상적으로 비교할 수 있게 되었다.

# 주요 설계 결정

## 1. 인증 검사를 Controller가 아닌 Security Filter에 위임

보호된 URL을 `authenticated()`로 설정하여 인증되지 않은 요청이 Controller까지 도달하지 않도록 했다.

이로 인해 각 Controller에서 반복하던 다음 코드를 제거할 수 있었다.

```java
if (loginMember == null) {
    return "redirect:/login";
}
```

인증은 Security Filter가 담당하고, Controller는 비즈니스 요청 처리에 집중하도록 역할을 분리했다.

---

## 2. Entity 대신 인증 전용 Principal 사용

`Member` Entity를 Security Context에 직접 저장하지 않고 인증에 필요한 정보만 가진 `LoginMemberPrincipal`을 사용했다.

이를 통해 인증 계층과 영속성 계층의 결합을 줄였다.

---

## 3. 서로 다른 Entity를 화면 DTO로 통합

목표와 성장 기록을 Entity 상속 구조로 변경하지 않고 화면 전용 `TimelineItem` DTO로 변환했다.

도메인 모델을 불필요하게 변경하지 않으면서 타임라인 UI에 필요한 공통 구조를 만들 수 있었다.

---

## 4. 기간 조회에 반개구간 사용

월별 조회 조건을 다음과 같이 구성했다.

```text
시작 시각 이상
&&
다음 달 시작 시각 미만
```

예시는 다음과 같다.

```text
createdAt >= 2026-07-01 00:00:00
createdAt < 2026-08-01 00:00:00
```

이 방식은 월별 마지막 날짜와 마지막 시간을 별도로 계산하지 않아도 되며, 밀리초나 나노초 단위의 데이터 누락도 방지할 수 있다.

# 오늘의 회고

오늘은 기존 세션 중심 인증 구조를 Spring Security 기반으로 전환하는 작업을 진행했다.

로그인 처리만 변경하면 기존 Controller가 동작하지 않을 수 있어 `LoginSuccessHandler`를 이용한 임시 호환 계층을 두고, 목표와 성장 기록 Controller부터 단계적으로 Principal 기반 인증으로 전환했다.

타임라인은 정적인 화면에서 실제 목표와 성장 기록을 통합해 보여주는 기능으로 확장했다. 서로 다른 Entity를 화면 전용 DTO로 변환하고 생성 시간 기준으로 정렬함으로써 도메인 구조를 크게 변경하지 않고 통합 목록을 구성했다.

환경별 설정도 분리하면서 소스 코드에 직접 작성되어 있던 DB와 메일 설정을 환경변수로 이동했다.

다음 작업에서는 남아 있는 세션 의존성을 제거하고 CSRF 보호 및 인증 통합 테스트를 보완할 예정이다.

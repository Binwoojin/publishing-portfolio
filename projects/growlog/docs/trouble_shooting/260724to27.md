# Part 1. 2026.07.24 — Attendance 및 MyPage

## 2. Attendance 달력의 `calendarElement`가 정의되지 않는 문제

### 문제 상황

Attendance 페이지에 월별 달력을 출력하기 위해 `attendance.js`에서 달력 렌더링 함수를 실행했지만 다음과 같은 JavaScript 오류가 발생하였다.

```text
calendarElement is not defined
```

또는 달력이 화면에 전혀 출력되지 않았다.

---

### 원인

달력 DOM 요소를 담을 `calendarElement` 변수를 선언하지 않은 상태에서 사용했거나, 특정 함수 안에서 선언한 변수를 다른 함수에서 참조하고 있었다.

예를 들어 다음과 같은 구조에서는 `calendarElement`를 사용할 수 없다.

```javascript
document.addEventListener("DOMContentLoaded", function () {
    const calendarElement =
        document.querySelector(".attendance-calendar");
});

renderCalendar(calendarElement);
```

`const`로 선언한 변수는 선언된 블록 내부에서만 사용할 수 있기 때문이다.

또한 DOM이 생성되기 전에 JavaScript가 실행될 경우 `querySelector()`의 결과가 `null`이 될 수 있다.

---

### 해결 방법

DOM이 완전히 생성된 이후 달력 요소를 조회하고, 조회한 요소를 함수의 매개변수로 전달하였다.

```javascript
document.addEventListener("DOMContentLoaded", function () {

    // Attendance 페이지의 달력 컨테이너를 조회한다.
    const calendarElement =
        document.querySelector(
            ".attendance-calendar"
        );

    // 현재 페이지에 달력 요소가 없으면
    // 이후 렌더링 작업을 실행하지 않는다.
    if (!calendarElement) {
        return;
    }

    const attendanceData =
        window.attendanceData || {};

    const attendedDays =
        attendanceData.attendedDays || [];

    renderCalendar(
        calendarElement,
        attendedDays
    );
});
```

렌더링 함수에서는 전역 변수를 참조하지 않고 전달받은 요소를 사용하도록 수정하였다.

```javascript
function renderCalendar(
        calendarElement,
        attendedDays
) {
    // 전달받은 달력 요소에 날짜를 생성한다.
}
```

---

### 결과

* `calendarElement is not defined` 오류 해결
* DOM 생성 이후 달력 렌더링 실행
* Attendance 페이지가 아닌 다른 페이지에서 JavaScript를 불러와도 오류가 발생하지 않음
* 함수가 외부 변수에 의존하지 않도록 구조 개선

---

### 배운 점

* `const`와 `let`은 블록 스코프를 가진다.
* DOM 요소는 `DOMContentLoaded` 이후 조회하는 것이 안전하다.
* `querySelector()` 결과는 항상 존재한다고 가정하면 안 된다.
* 함수에서 필요한 값은 전역 변수보다 매개변수로 전달하는 것이 유지보수에 유리하다.

## 3. 성장 기록을 작성했지만 달력에 출석 표시가 나타나지 않는 문제

### 문제 상황

출석 인정 조건에 맞게 성장 기록을 한 건 작성했지만 Attendance 달력의 해당 날짜에 출석 표시가 나타나지 않았다.

백엔드에서는 성장 기록 데이터가 정상적으로 조회되고 있었지만 화면에서는 출석 날짜가 반영되지 않았다.

---

### 원인

서버에서 계산한 `attendedDays` 목록을 JSP에서 JavaScript 배열로 변환하는 과정에 문제가 있었다.

가능한 원인은 다음과 같았다.

```text
JSP의 Model 이름 불일치
JSTL 반복문의 변수명 오류
쉼표 처리 오류
JavaScript 객체 속성명 불일치
attendance.js 실행 시점 문제
```

예를 들어 쉼표 처리가 올바르지 않으면 다음과 같은 잘못된 JavaScript가 생성될 수 있다.

```javascript
attendedDays: [
    2425
]
```

또는 마지막 값 뒤에 불필요한 쉼표나 JSP 문자열이 포함될 수 있었다.

---

### 해결 방법

JSTL의 `varStatus`를 사용하여 마지막 요소를 제외하고 쉼표를 출력하도록 수정하였다.

```jsp
<script>
    window.attendanceData = {
        attendedDays: [
            <c:forEach
                items="${attendanceSummary.attendedDays}"
                var="day"
                varStatus="status"
            >
                ${day}<c:if test="${!status.last}">,</c:if>
            </c:forEach>
        ]
    };
</script>
```

JavaScript에서도 데이터가 없을 가능성을 고려하여 기본값을 지정하였다.

```javascript
const attendanceData =
    window.attendanceData || {};

const attendedDays =
    attendanceData.attendedDays || [];
```

브라우저 개발자 도구에서 최종 생성된 값을 확인하였다.

```javascript
window.attendanceData = {
    attendedDays: [1, 5, 12, 24]
};
```

---

### 결과

* 서버에서 계산한 출석 날짜가 JavaScript 배열로 정상 전달됨
* 성장 기록을 작성한 날짜가 달력에 정상 표시됨
* 데이터가 없는 회원도 JavaScript 오류 없이 빈 달력 출력
* 백엔드 계산 문제와 프런트 데이터 전달 문제를 구분하여 해결

---

### 배운 점

* 서버의 데이터가 정상이어도 JSP에서 JavaScript로 변환하는 과정에서 오류가 발생할 수 있다.
* JSP가 생성한 최종 HTML과 JavaScript를 브라우저 개발자 도구에서 확인해야 한다.
* JSTL 반복문으로 배열을 만들 때 마지막 쉼표 처리를 주의해야 한다.
* 백엔드, JSP, JavaScript의 변수명을 일관되게 유지해야 한다.

## 4. `GrowthRecordService.countRecordsByMember()` 메서드가 존재하지 않는 문제

### 문제 상황

AttendanceService에서 회원의 성장 기록 수를 조회하기 위해 다음 메서드를 호출하려 했지만 컴파일 오류가 발생하였다.

```java
growthRecordService.countRecordsByMember(memberNo);
```

---

### 원인

실제 `GrowthRecordService` 클래스에는 `countRecordsByMember()`라는 메서드가 구현되어 있지 않았다.

AttendanceService를 구현하면서 존재할 것으로 예상한 메서드명을 사용했지만, 기존 프로젝트의 Service와 Repository 구조를 확인하지 않고 작성한 것이 원인이었다.

---

### 해결 방법

기존 `GrowthRecordRepository`에 있는 메서드를 확인하고 실제 존재하는 메서드를 사용하였다.

```java
long recordCount =
        growthRecordRepository
                .countByMemberMemberNo(memberNo);
```

날짜별 출석 계산에는 단순한 전체 개수보다 성장 기록의 작성 날짜가 필요하므로 회원별 기록 조회 또는 날짜 범위 조회 메서드를 사용하도록 역할을 구분하였다.

```text
전체 기록 수
→ countByMemberMemberNo()

출석 날짜 계산
→ 회원별 성장 기록 날짜 조회
```

---

### 결과

* 존재하지 않는 Service 메서드 호출 문제 해결
* 기존 Repository 메서드를 재사용
* Attendance 계산에 필요한 데이터와 단순 카운트 데이터의 차이 명확화

---

### 배운 점

* 새로운 기능에서 기존 Service를 사용할 때는 실제 구현된 메서드를 먼저 확인해야 한다.
* 메서드 이름을 예상해서 작성하기보다 Repository와 Service의 현재 책임을 확인해야 한다.
* 출석 계산에는 전체 개수보다 날짜 데이터가 중요하다.
* Service가 다른 Service를 과도하게 의존하는 구조보다 필요한 Repository를 직접 사용하는 편이 적절한 경우도 있다.

## 5. `MyPageController`의 중복 매핑 오류

### 문제 상황

프로젝트를 실행할 때 다음과 유사한 오류가 발생하였다.

```text
Ambiguous mapping
Cannot map 'myPageController' method
```

특히 `/mypage/profile` 요청을 처리하는 메서드가 중복으로 등록되어 있었다.

---

### 원인

같은 Controller 또는 서로 다른 Controller에서 동일한 HTTP Method와 URL을 사용하였다.

예를 들면 다음 두 메서드는 동일한 요청을 처리하려고 하기 때문에 충돌한다.

```java
@GetMapping("/profile")
public String myPageProfile() {
    return "mypage/profile";
}
```

```java
@GetMapping("/profile")
public String profilePage() {
    return "mypage/profile";
}
```

클래스에 다음 공통 매핑이 있다면 두 메서드 모두 최종 URL은 `/mypage/profile`이 된다.

```java
@RequestMapping("/mypage")
```

---

### 해결 방법

프로젝트 전체에서 `/mypage/profile` 매핑을 검색하고 하나의 메서드만 남겼다.

```java
@Controller
@RequiredArgsConstructor
@RequestMapping("/mypage")
public class MyPageController {

    @GetMapping("/profile")
    public String profilePage(
            HttpSession session,
            Model model
    ) {
        Member loginMember =
                getLoginMember(session);

        if (loginMember == null) {
            return "redirect:/login";
        }

        model.addAttribute(
                "loginMember",
                loginMember
        );

        return "mypage/profile";
    }
}
```

MyPage 기본 주소는 프로필 페이지로 리다이렉트하도록 분리하였다.

```java
@GetMapping
public String myPage() {
    return "redirect:/mypage/profile";
}
```

---

### 결과

* Spring Boot 실행 시 `Ambiguous mapping` 오류 해결
* MyPage URL 구조 정리
* `/mypage`와 `/mypage/profile`의 역할 분리
* Controller 메서드 책임이 명확해짐

---

### 배운 점

* Spring의 요청 매핑은 메서드명이 아니라 HTTP Method와 URL 조합으로 구분된다.
* 클래스의 `@RequestMapping`과 메서드의 `@GetMapping`을 합친 최종 URL을 확인해야 한다.
* 새로운 매핑을 추가하기 전에 프로젝트 전체 검색으로 중복 여부를 확인하는 것이 좋다.
* 기본 페이지는 별도의 View를 만들거나 하위 페이지로 리다이렉트할 수 있다.

---

## 6. `mypage.jsp`를 찾지 못하는 View 경로 문제

### 문제 상황

MyPage로 이동했을 때 JSP를 찾지 못하거나 404 오류가 발생하였다.

Controller에서는 다음과 같이 반환하고 있었다.

```java
return "mypage";
```

하지만 실제 프로젝트에는 `mypage.jsp`가 존재하지 않았다.

---

### 원인

Controller의 View 이름과 실제 JSP 폴더 구조가 일치하지 않았다.

View Resolver 설정이 다음과 같다면,

```text
prefix: /WEB-INF/views/
suffix: .jsp
```

`return "mypage";`는 다음 파일을 찾는다.

```text
/WEB-INF/views/mypage.jsp
```

하지만 실제 파일은 다음 위치에 있었다.

```text
/WEB-INF/views/mypage/profile.jsp
/WEB-INF/views/mypage/attendance.jsp
/WEB-INF/views/mypage/settings.jsp
```

---

### 해결 방법

Controller가 실제 JSP 경로와 일치하는 View 이름을 반환하도록 수정하였다.

```java
return "mypage/profile";
```

각 페이지도 동일한 방식으로 정리하였다.

```java
return "mypage/attendance";
return "mypage/settings";
return "mypage/settings-verify";
```

MyPage 기본 URL에서는 존재하지 않는 View를 반환하지 않고 프로필로 리다이렉트하였다.

```java
@GetMapping
public String myPage() {
    return "redirect:/mypage/profile";
}
```

---

### 결과

* 존재하지 않는 `mypage.jsp` 탐색 문제 해결
* Controller와 JSP 폴더 구조 통일
* MyPage 하위 메뉴별 화면 정상 출력

---

### 배운 점

다음 세 가지는 서로 다른 개념이다.

```text
요청 URL
→ /mypage/profile

Controller의 View 이름
→ mypage/profile

실제 JSP 경로
→ /WEB-INF/views/mypage/profile.jsp
```

View 오류가 발생하면 URL만 확인하지 말고 Controller 반환 문자열과 실제 파일 경로를 함께 확인해야 한다.

## 7. MyPage 메뉴의 `<a>` 태그 중첩으로 레이아웃이 깨지는 문제

### 문제 상황

MyPage의 퀵 메뉴를 클릭 가능한 카드로 변경한 뒤 `flex` 정렬이 깨지고 클릭 영역이 예상과 다르게 동작하였다.

---

### 원인

기존 카드 내부에 링크가 있었는데 카드 전체를 다시 `<a>` 태그로 감싸면서 링크 태그가 중첩되었다.

```jsp
<a href="/mypage/settings">
    <div class="menu-card">
        <a href="/mypage/settings">
            계정 설정
        </a>
    </div>
</a>
```

HTML에서는 `<a>` 태그 안에 또 다른 `<a>` 태그를 넣는 구조가 올바르지 않다.

브라우저가 DOM 구조를 자동으로 보정하면서 CSS의 `flex` 대상과 클릭 영역도 달라졌다.

---

### 해결 방법

메뉴 카드 하나당 하나의 링크만 사용하였다.

```jsp
<a
    href="${pageContext.request.contextPath}/mypage/settings/verify"
    class="mypage-menu-item"
>
    <span class="mypage-menu-icon">
        <!-- 아이콘 -->
    </span>

    <span class="mypage-menu-text">
        계정 설정
    </span>
</a>
```

CSS도 링크 자체를 flex 컨테이너로 설정하였다.

```css
.mypage-menu-item {
    display: flex;
    align-items: center;
    gap: 14px;

    color: inherit;
    text-decoration: none;
}
```

---

### 결과

* 메뉴 카드 레이아웃 정상화
* 카드 전체 클릭 가능
* 클릭 이벤트 중첩 문제 해결
* HTML 구조 단순화

---

### 배운 점

* `<a>` 태그는 중첩해서 사용하면 안 된다.
* 카드 전체를 클릭하게 만들 때는 가장 바깥 요소 하나만 링크로 사용한다.
* 불필요하게 `<div>`와 `<a>`를 여러 겹으로 만들기보다 역할을 단순화하는 것이 좋다.

## 8. 계정 설정 요청에서 405 Method Not Allowed가 발생한 문제

### 문제 상황

계정 설정 화면에서 닉네임 또는 비밀번호 변경 form을 제출했을 때 다음 오류가 발생하였다.

```text
405 Method Not Allowed
```

---

### 원인

JSP form은 `POST` 방식으로 요청하고 있었지만 Controller에 해당 URL의 `@PostMapping`이 없거나 다른 URL로 매핑되어 있었다.

예를 들어 JSP는 다음 주소로 요청하지만,

```jsp
<form
    action="${pageContext.request.contextPath}/mypage/settings"
    method="post"
>
```

Controller에는 GET 요청만 존재하면 POST 요청을 처리할 수 없다.

```java
@GetMapping("/settings")
public String settingsPage() {
    return "mypage/settings";
}
```

---

### 해결 방법

form의 목적에 따라 POST 요청 URL을 분리하고 Controller에 해당 매핑을 추가하였다.

```java
@PostMapping("/settings/nickname")
public String updateNickname(
        @RequestParam String nickname,
        HttpSession session,
        RedirectAttributes redirectAttributes
) {
    // 닉네임 변경 처리

    return "redirect:/mypage/settings";
}
```

```java

public String updatePassword(
        @RequestParam String currentPassword,
        @RequestParam String newPassword,
        @RequestParam String confirmPassword,
        HttpSession session,
```

## 9. 인증번호 발송 후 다음 화면으로 전환되지 않는 문제

### 문제 상황

이메일 인증번호 발송은 정상적으로 처리되었지만 화면에는 계속 이메일 입력 form만 표시되었다.

사용자는 인증번호를 입력할 수 없었다.

---

### 원인

JSP는 `codeSent` 값에 따라 화면 단계를 구분하고 있었지만 POST 요청을 처리한 Controller에서 해당 값을 Model에 다시 전달하지 않았다.

```jsp
<c:if test="${not codeSent}">
    <!-- 이메일 입력 -->
</c:if>

<c:if test="${codeSent}">
    <!-- 인증번호 입력 -->
</c:if>
```

Model 값은 현재 요청 동안만 유지되므로 다음 요청에서는 자동으로 남아 있지 않는다.

또한 JSP에서 사용하는 변수명과 Controller에서 전달하는 이름이 다르면 항상 첫 번째 단계만 출력된다.

---

### 해결 방법

인증번호 발송 성공 후 `codeSent`를 Model에 추가하였다.

```java
model.addAttribute("codeSent", true);
model.addAttribute(
        "successMessage",
        "인증번호를 이메일로 발송했습니다."
);

return "find-password";
```

페이지 진입 시에는 세션에 저장된 재설정 이메일과 인증 상태를 바탕으로 화면 단계를 복원하도록 보완하였다.

```java
String resetEmail =
        (String) session.getAttribute(
                "PASSWORD_RESET_EMAIL"
        );

Boolean verified =
        (Boolean) session.getAttribute(
                "PASSWORD_RESET_VERIFIED"
        );

model.addAttribute(
        "codeSent",
        resetEmail != null
);

model.addAttribute(
        "verified",
        Boolean.TRUE.equals(verified)
);
```

---

### 결과

* 인증번호 발송 후 인증번호 입력 화면으로 정상 전환
* 새로고침 또는 검증 실패 후에도 현재 단계 복원
* Controller와 JSP의 상태값 통일

---

### 배운 점

* Model Attribute는 현재 요청에서만 유지된다.
* 여러 단계로 구성된 form은 서버가 현재 진행 상태를 명확하게 관리해야 한다.
* 중요한 인증 상태는 단순한 JSP 변수보다 세션에 저장하는 것이 안정적이다.

## 10. 인증번호가 틀리면 이메일 입력 화면으로 돌아가는 문제

사용자는 이메일 발송 단계부터 다시 진행해야 했다.

### 원인

```java
model.addAttribute(
        "errorMessage",
        "인증번호가 일치하지 않습니다."
);

```

JSP 입장에서는 `codeSent` 값이 없으므로 첫 번째 form을 출력하였다.

```java
model.addAttribute("codeSent", true);
model.addAttribute("verified", false);

        "errorMessage",
        "인증번호가 일치하지 않습니다."
```

### 결과

## 11. 인증 완료 후 새 비밀번호 입력 화면이 나타나지 않는 문제

---

### 원인

인증 성공 후 세션에는 `PASSWORD_RESET_VERIFIED` 값을 저장했지만 JSP에서 사용하는 `verified` Model 값이 전달되지 않았거나 조건식이 잘못 구성되어 있었다.

```jsp
<c:if test="${verified}">
    <!-- 새 비밀번호 설정 -->
</c:if>
```

또는 인증번호 입력 영역의 조건이 너무 넓어 인증 완료 후에도 함께 출력될 수 있었다.

---

### 해결 방법

```java
session.setAttribute(
        "PASSWORD_RESET_VERIFIED",
        true
);

model.addAttribute("codeSent", true);
model.addAttribute("verified", true);
```

JSP 조건도 단계별로 겹치지 않도록 구성하였다.

```jsp
<c:if test="${not codeSent}">
    <!-- 이메일 입력 단계 -->
</c:if>

<c:if test="${codeSent and not verified}">
    <!-- 인증번호 확인 단계 -->
</c:if>

<c:if test="${verified}">
    <!-- 새 비밀번호 설정 단계 -->
</c:if>
```

---

### 결과

* 인증 성공 후 새 비밀번호 설정 화면 정상 출력
* 여러 form이 동시에 출력되는 문제 방지
* 인증 단계가 명확하게 분리됨

---

### 배운 점

* 조건부 화면은 조건이 서로 겹치지 않도록 설계해야 한다.
* 보안상 중요한 인증 상태는 세션에서 관리하되 화면 출력을 위한 Model 값도 일관되게 전달해야 한다.
* Boolean 값은 `Boolean.TRUE.equals()`를 사용하면 `null`에 안전하다.

# Part 3. 2026.07.27 — AWS S3 및 Media

## 16. `createPresignedUrl()` 메서드가 비어 있어 이미지를 조회할 수 없는 문제

### 문제 상황

S3에 이미지를 업로드하고 Media 데이터도 저장할 수 있었지만, 비공개 S3 객체를 화면에서 조회할 URL을 생성할 수 없었다.

`S3FileStorageService`의 메서드는 다음과 같이 비어 있었다.

```java
public String createPresignedUrl(
        String objectKey
) {

}
```

---

### 원인

비공개 S3 버킷의 객체는 일반 Object URL만으로 접근할 수 없다.

이미지를 사용자 화면에 표시하려면 일정 시간 동안 접근 가능한 서명 URL을 생성해야 하지만 해당 로직이 구현되지 않았다.

---

### 해결 방법

`GetObjectRequest`, `GetObjectPresignRequest`, `S3Presigner`를 사용하여 Presigned URL을 생성하였다.

```java
public String createPresignedUrl(
        String objectKey
) {
    // 접근할 S3 객체의 정보를 설정한다.
    GetObjectRequest getObjectRequest =
            GetObjectRequest.builder()
                    .bucket(bucketName)
                    .key(objectKey)
                    .build();

    // 생성할 URL의 유효 시간과
    // S3 조회 요청 정보를 설정한다.
    GetObjectPresignRequest presignRequest =
            GetObjectPresignRequest.builder()
                    .signatureDuration(
                            Duration.ofMinutes(10)
                    )
                    .getObjectRequest(
                            getObjectRequest
                    )
                    .build();

    // 서명된 임시 접근 URL을 생성한다.
    PresignedGetObjectRequest
            presignedRequest =
            s3Presigner.presignGetObject(
                    presignRequest
            );

    return presignedRequest
            .url()
            .toString();
}
```

---

### 결과

* 비공개 S3 이미지의 임시 조회 URL 생성 가능
* 버킷을 Public으로 설정하지 않고 이미지 출력 가능
* URL 유효 시간을 10분으로 제한

---

### 배운 점

* 비공개 S3 객체는 Presigned URL을 통해 제한적으로 접근할 수 있다.
* Presigned URL은 접근 권한을 일시적으로 위임하는 URL이다.
* URL 생성 전에도 애플리케이션 차원의 회원 권한 검증이 필요하다.

## 17. `S3Presigner` Bean을 주입할 수 없는 문제

### 문제 상황

`S3FileStorageService`에 다음 의존성을 추가한 뒤 Bean을 찾을 수 없다는 오류가 발생할 수 있었다.

```java
private final S3Presigner s3Presigner;
```

---

### 원인

프로젝트에는 파일 업로드용 `S3Client` Bean만 등록되어 있었고 `S3Presigner` Bean은 등록되어 있지 않았다.

Spring은 생성자 주입 시 등록된 Bean만 주입할 수 있다.

---

### 해결 방법

`S3Config`에 `S3Presigner` Bean을 추가하였다.

```java
@Bean
public S3Presigner s3Presigner(
        AwsCredentialsProvider
                credentialsProvider
) {
    return S3Presigner.builder()
            .region(
                    Region.AP_NORTHEAST_2
            )
            .credentialsProvider(
                    credentialsProvider
            )
            .build();
}
```

---

### 결과

* `S3FileStorageService`에 `S3Presigner` 정상 주입
* Presigned URL 생성 기능 실행 가능
* S3Client와 동일한 Region 및 인증 정보 사용

---

### 배운 점

* SDK 객체를 생성자 주입하려면 Spring Bean으로 등록해야 한다.
* `S3Client`와 `S3Presigner`는 서로 다른 객체이며 역할도 다르다.

```text
S3Client
→ 업로드, 삭제, 객체 관리

S3Presigner
→ 서명된 임시 접근 URL 생성
```

---

## 18. `credentialsProvider()` 호출에서 오류가 발생한 문제

### 문제 상황

`S3Presigner` Bean을 다음과 같이 구성했지만 `credentialsProvider()` 부분에서 오류가 발생하였다.

```java
@Bean
public S3Presigner s3Presigner() {
    return S3Presigner.builder()
            .region(
                    Region.AP_NORTHEAST_2
            )
            .credentialsProvider(
                    credentialsProvider()
            )
            .build();
}
```

---

### 원인

다음 중 하나가 원인이 될 수 있었다.

```text
credentialsProvider() 메서드가 존재하지 않음
메서드 반환 타입 불일치
필요한 AWS SDK import 누락
설정 클래스에서 인증 Bean을 정의하지 않음
```

또한 Bean 메서드를 직접 호출하는 방식보다 필요한 Bean을 메서드 파라미터로 주입하는 편이 구성 관계가 명확하다.

---

### 해결 방법

공통으로 사용할 `AwsCredentialsProvider` Bean을 별도로 등록하였다.

```java
@Bean
public AwsCredentialsProvider
credentialsProvider(
        @Value(
            "${cloud.aws.credentials.access-key}"
        )
        String accessKey,

        @Value(
            "${cloud.aws.credentials.secret-key}"
        )
        String secretKey
) {
    AwsBasicCredentials credentials =
            AwsBasicCredentials.create(
                    accessKey,
                    secretKey
            );

    return StaticCredentialsProvider.create(
            credentials
    );
}
```

이후 `S3Client`와 `S3Presigner`가 해당 Bean을 파라미터로 주입받도록 수정하였다.

```java
@Bean
public S3Client s3Client(
        AwsCredentialsProvider
                credentialsProvider
) {
    return S3Client.builder()
            .region(
                    Region.AP_NORTHEAST_2
            )
            .credentialsProvider(
                    credentialsProvider
            )
            .build();
}
```

```java
@Bean
public S3Presigner s3Presigner(
        AwsCredentialsProvider
                credentialsProvider
) {
    return S3Presigner.builder()
            .region(
                    Region.AP_NORTHEAST_2
            )
            .credentialsProvider(
                    credentialsProvider
            )
            .build();
}
```

---

### 결과

* `credentialsProvider()` 관련 컴파일 및 Bean 구성 오류 해결
* S3Client와 S3Presigner에서 동일한 인증 정보 재사용
* AWS 설정 코드의 중복 감소
* Bean 의존 관계 명확화

---

### 배운 점

* AWS SDK v2에서는 `AwsCredentialsProvider` 타입을 사용한다.
* 여러 AWS Client가 같은 인증 정보를 사용한다면 공통 Bean으로 분리하는 것이 좋다.
* `@Bean` 메서드 파라미터를 통한 주입은 Bean 간 의존성을 명확하게 표현한다.
* 잘못된 import가 포함되어 있지 않은지도 확인해야 한다.

주요 import는 다음과 같다.

```java
import software.amazon.awssdk.auth.credentials.AwsBasicCredentials;
import software.amazon.awssdk.auth.credentials.AwsCredentialsProvider;
import software.amazon.awssdk.auth.credentials.StaticCredentialsProvider;
```

---

## 19. MediaService에서 Presigned URL을 DB에 저장해야 하는지 혼선이 발생한 문제

### 문제 상황

이미지를 S3에 업로드한 후 Media Entity의 `mediaUrl` 필드에 다음 중 어떤 값을 저장해야 하는지 혼선이 있었다.

```text
S3 Object Key
또는
Presigned URL
```

---

### 원인

필드명이 `mediaUrl`이기 때문에 실제 브라우저에서 접근할 수 있는 전체 URL을 저장해야 할 것처럼 보였다.

하지만 Presigned URL에는 만료 시간이 존재한다.

예를 들어 10분짜리 URL을 DB에 저장하면 10분 후에는 사용할 수 없는 주소가 DB에 남게 된다.

---

### 해결 방법

DB에는 만료되지 않는 S3 Object Key만 저장하도록 결정하였다.

```java
String objectKey =
        s3FileStorageService.uploadImage(
                imageFile,
                memberNo
        );

Media media =
        Media.builder()
                .growthRecord(growthRecord)
                .mediaType(MediaType.IMAGE)
                .mediaUrl(objectKey)
                .sortOrder(sortOrder)
                .build();
```

이미지를 화면에 출력할 때만 Object Key를 이용해 Presigned URL을 생성한다.

```java
String imageUrl =
        s3FileStorageService
                .createPresignedUrl(
                        media.getMediaUrl()
                );
```

전체 구조는 다음과 같다.

```text
이미지 등록
→ S3 업로드
→ Object Key 반환
→ Object Key를 DB에 저장

이미지 조회
→ DB에서 Object Key 조회
→ Presigned URL 생성
→ JSP 또는 DTO에 전달
```

---

### 결과

* 만료된 URL이 DB에 남는 문제 방지
* S3 저장 정보와 화면 접근 URL의 역할 분리
* URL 유효 시간을 자유롭게 변경 가능
* 버킷 또는 도메인 구성이 바뀌어도 DB 수정 필요 감소

---

### 배운 점

* 데이터베이스에는 가능한 한 영속적인 식별값을 저장해야 한다.
* Presigned URL은 영속 데이터가 아니라 조회 시 생성되는 임시 데이터이다.
* 필드명이 `mediaUrl`이더라도 실제 저장 의미가 Object Key라면 추후 `objectKey` 또는 `storageKey`로 이름을 변경하는 것도 고려할 수 있다.

---

## 20. AWS 인증 정보를 코드나 설정 파일에 직접 노출할 위험

### 문제 상황

S3Client와 S3Presigner 설정을 위해 Access Key와 Secret Key가 필요했지만 실제 값을 Java 코드나 GitHub에 업로드되는 설정 파일에 직접 작성할 위험이 있었다.

---

### 원인

테스트 편의를 위해 인증 정보를 다음과 같이 직접 작성하기 쉽다.

```java
AwsBasicCredentials.create(
        "실제_ACCESS_KEY",
        "실제_SECRET_KEY"
);
```

또는 `application.yaml`에 실제 값을 그대로 작성할 수 있다.

이는 GitHub에 Push할 경우 AWS 계정 보안 사고로 이어질 수 있다.

---

### 해결 방법

설정 파일에는 환경 변수 이름만 작성하였다.

```yaml
cloud:
  aws:
    credentials:
      access-key: ${AWS_ACCESS_KEY}
      secret-key: ${AWS_SECRET_KEY}

    s3:
      bucket: ${AWS_S3_BUCKET}
```

실제 값은 로컬 실행 환경이나 배포 환경에서 별도로 설정하도록 하였다.

---

### 결과

* AWS 인증 정보의 GitHub 노출 방지
* 개발 환경과 배포 환경에서 서로 다른 인증 정보 사용 가능
* 설정과 코드 분리

---

### 배운 점

* Access Key와 Secret Key는 비밀번호와 동일하게 취급해야 한다.
* 이미 GitHub에 노출되었다면 단순히 파일을 삭제하는 것으로 끝나지 않고 해당 키를 즉시 폐기하고 새 키를 발급해야 한다.
* 환경 변수와 `.gitignore`를 함께 활용해야 한다.

# Part 4. 공통 분석

## 21. 세 날짜의 문제에서 공통적으로 확인한 원인

이번 오류들은 서로 다른 기능에서 발생했지만 공통적인 원인을 가지고 있었다.

### 1. 계층 사이의 이름과 계약 불일치

```text
Controller Model 이름
↔ JSP EL 이름

JSP form action
↔ Controller Mapping

JSP JavaScript 속성명
↔ JavaScript 참조 이름

Spring Bean 타입
↔ 생성자 주입 타입
```

각 계층은 독립적으로 정상이어도 연결되는 이름이나 타입이 일치하지 않으면 기능 전체가 작동하지 않는다.

---

### 2. 임시 상태와 영속 데이터의 구분 부족

```text
인증번호
→ 세션의 임시 데이터

인증 완료 상태
→ 비밀번호 변경까지만 필요한 임시 상태

Presigned URL
→ 일정 시간만 유효한 임시 URL

S3 Object Key
→ DB에 저장할 영속 데이터
```

임시로 사용해야 할 값을 DB에 저장하거나, 요청이 바뀔 때 사라지는 Model에만 의존하면 문제가 발생한다.

---

### 3. 기능 구현 이후 실패 경로 점검 부족

정상 흐름만 확인하면 다음 문제를 놓칠 수 있다.

```text
인증번호가 틀렸을 때
인증번호가 만료되었을 때
DOM 요소가 없을 때
데이터 목록이 비어 있을 때
동일 URL 매핑이 이미 있을 때
Bean이 등록되지 않았을 때
Presigned URL이 만료되었을 때
```

성공 경로뿐 아니라 실패와 예외 상황도 함께 테스트해야 한다.

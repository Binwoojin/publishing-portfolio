## 1. 이미지 파일이 요청 DTO에 바인딩되지 않는 문제

### 문제 상황

성장 기록 작성 화면에서 여러 이미지를 선택했지만 서버의 `GrowthRecordRequest`에서 이미지 목록을 정상적으로 전달받지 못했다.

### 원인

JSP의 파일 입력 필드 이름은 `imageFiles`였지만 DTO 필드명은 `imageFile`로 정의되어 있었다.

Spring MVC는 HTML의 `name` 속성과 DTO 필드명을 기준으로 요청 데이터를 바인딩한다. 두 이름이 다르면 업로드한 파일 목록이 DTO에 저장되지 않는다.

또한 파일을 서버로 전송하는 form에는 `multipart/form-data` 설정이 필요하다.

### 해결 방법

DTO 필드명을 JSP의 파일 입력 필드 이름과 동일한 `imageFiles`로 수정했다.

```java
private List<MultipartFile> imageFiles;
```

작성 및 수정 form에는 `enctype="multipart/form-data"`를 추가했다.

```jsp
<form
    method="post"
    enctype="multipart/form-data"
>
    <input
        type="file"
        name="imageFiles"
        multiple
    >
</form>
```

Service에서도 단일 파일 getter가 아닌 다중 파일 목록을 반환하는 메서드를 사용하도록 수정했다.

```java
request.getImageFiles();
```

### 결과

여러 이미지가 `List<MultipartFile>` 형태로 정상 바인딩되어 S3 업로드 로직에 전달되었다.

### 배운 점

* HTML의 `name` 속성과 DTO 필드명은 반드시 일치해야 한다.
* 파일 업로드 form에는 `multipart/form-data` 설정이 필요하다.
* 다중 파일 업로드 시 DTO 필드 타입은 `List<MultipartFile>` 또는 배열 형태로 구성해야 한다.

## 2. AWS 자격 증명을 찾지 못하는 문제

### 문제 상황

애플리케이션 실행 또는 이미지 업로드 과정에서 AWS 자격 증명을 찾지 못해 S3 요청이 실패했다.

```text
Unable to load credentials from any of the providers in the chain
```

### 원인

기존 설정이 특정 환경변수 이름에만 의존하고 있었다.

```yaml
access-key: ${AWS_ACCESS_KEY}
secret-key: ${AWS_SECRET_KEY}
```

하지만 실행 환경에 따라 AWS SDK의 표준 환경변수인 다음 값을 사용할 수 있다.

```text
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
```

또한 설정 파일에 Access Key와 Secret Key가 존재하더라도 `DefaultCredentialsProvider`만 사용하면 해당 설정값이 명시적인 자격 증명 Provider에 반영되지 않을 수 있었다.

### 해결 방법

기존 환경변수와 AWS 표준 환경변수를 모두 지원하도록 설정했다.

```yaml
cloud:
  aws:
    credentials:
      access-key: ${AWS_ACCESS_KEY:${AWS_ACCESS_KEY_ID:}}
      secret-key: ${AWS_SECRET_KEY:${AWS_SECRET_ACCESS_KEY:}}

    region:
      static: ${AWS_REGION:ap-northeast-2}
```

Access Key와 Secret Key가 명시적으로 제공된 경우 `StaticCredentialsProvider`를 사용하도록 구성했다.

```java
if (hasAccessKey) {
    return StaticCredentialsProvider.create(
        AwsBasicCredentials.create(
            accessKey.trim(),
            secretKey.trim()
        )
    );
}
```

키가 제공되지 않은 경우에는 AWS SDK의 기본 자격 증명 탐색 방식을 사용했다.

```java
return DefaultCredentialsProvider
        .builder()
        .build();
```

Access Key와 Secret Key 중 하나만 설정된 경우에는 애플리케이션 시작 단계에서 오류를 발생시키도록 검증했다.

```java
if (hasAccessKey != hasSecretKey) {
    throw new IllegalStateException(
        "AWS Access Key와 Secret Key는 반드시 함께 설정해야 합니다."
    );
}
```

### 결과

다음과 같은 다양한 실행 환경에서 AWS 자격 증명을 사용할 수 있게 되었다.

* 프로젝트 전용 환경변수
* AWS 표준 환경변수
* AWS CLI Profile
* EC2 및 ECS IAM Role
* 기타 AWS SDK 기본 자격 증명 탐색 방식

### 배운 점

* AWS 표준 환경변수 이름과 프로젝트 전용 환경변수를 함께 지원하면 실행 환경 변화에 대응하기 쉽다.
* Access Key와 Secret Key는 반드시 한 쌍으로 설정되어야 한다.
* 로컬과 배포 환경에서는 서로 다른 자격 증명 방식을 사용할 수 있다.
* 운영 환경에서는 가능하면 고정 Access Key보다 IAM Role을 사용하는 것이 적절하다.

## 3. S3 오류의 실제 원인을 구분하기 어려운 문제

### 문제 상황

S3 업로드, 삭제 또는 Presigned URL 생성에 실패했을 때 유사한 예외만 발생해 정확한 원인을 확인하기 어려웠다.

### 원인

서로 다른 성격의 오류를 하나의 일반 예외로 처리하고 있었다.

```text
AWS 권한 또는 버킷 설정 오류
AWS 자격 증명 탐색 실패
네트워크 연결 실패
파일 읽기 실패
```

이로 인해 개발자가 오류 메시지만 보고 인증 문제인지, 권한 문제인지, 네트워크 문제인지 구분하기 어려웠다.

### 해결 방법

AWS 서버에서 응답한 오류와 SDK 클라이언트 측 오류를 구분해 처리했다.

```java
catch (S3Exception e) {
    throw new IllegalStateException(
        createS3ErrorMessage("업로드", e),
        e
    );
} catch (SdkClientException e) {
    throw new IllegalStateException(
        "AWS 자격 증명 또는 네트워크 문제로 "
            + "S3 이미지 업로드에 실패했습니다.",
        e
    );
}
```

AWS 응답 메시지를 포함하는 공통 메서드도 추가했다.

```java
private String createS3ErrorMessage(
        String operation,
        S3Exception exception
) {
    String awsMessage =
            exception.awsErrorDetails() == null
                    ? exception.getMessage()
                    : exception.awsErrorDetails()
                            .errorMessage();

    return "S3 이미지 "
            + operation
            + "에 실패했습니다. AWS 응답: "
            + awsMessage;
}
```

### 결과

오류 발생 시 다음 원인을 이전보다 명확하게 구분할 수 있게 되었다.

* AWS 권한 오류
* 버킷명 또는 Region 설정 오류
* 자격 증명 탐색 실패
* 네트워크 연결 문제
* AWS SDK 클라이언트 오류

### 배운 점

* `S3Exception`은 AWS 서버가 반환한 오류를 확인할 때 사용한다.
* `SdkClientException`은 자격 증명 탐색, 네트워크, SDK 설정 문제를 확인할 때 유용하다.
* 외부 서비스 연동 예외는 원인 유형별로 분리해 처리하는 것이 좋다.

## 4. 지원하지 않는 이미지 형식이 업로드될 수 있는 문제

### 문제 상황

이미지 파일 검증이 충분하지 않아 서비스에서 지원하지 않는 이미지 형식도 업로드될 가능성이 있었다.

### 원인

기존에는 MIME 타입이 `image/`로 시작하는지만 확인했다.

```java
contentType.startsWith("image/");
```

이 방식은 브라우저나 서버가 이미지로 인식하는 모든 MIME 타입을 허용한다.

또한 HTML의 `accept` 속성은 사용자의 파일 선택을 돕는 기능일 뿐 서버 검증을 대신할 수 없다.

### 해결 방법

서버에서 허용할 MIME 타입을 화이트리스트로 정의했다.

```java
private static final Set<String>
        ALLOWED_IMAGE_TYPES = Set.of(
            "image/jpeg",
            "image/png",
            "image/webp"
        );
```

업로드된 파일의 MIME 타입이 허용 목록에 포함되는지 검사했다.

```java
if (
    contentType == null
    || !ALLOWED_IMAGE_TYPES.contains(
        contentType.toLowerCase()
    )
) {
    throw new IllegalArgumentException(
        "JPG, PNG, WEBP 이미지 파일만 업로드할 수 있습니다."
    );
}
```

프론트엔드 파일 입력에도 동일한 형식을 지정했다.

```jsp
<input
    type="file"
    name="imageFiles"
    accept="image/jpeg, image/png, image/webp"
    multiple
>
```

### 결과

클라이언트와 서버에서 모두 JPG, PNG, WEBP 파일만 허용하게 되었다.

### 배운 점

* 프론트엔드의 `accept` 속성만으로 파일 형식을 제한할 수 없다.
* 서버 검증은 반드시 별도로 구현해야 한다.
* 허용되지 않은 형식을 차단할 때는 화이트리스트 방식이 안전하다.
* 확장자뿐 아니라 MIME 타입 검증도 함께 고려해야 한다.

## 5. 성장 기록 수정 시 이미지가 5장을 초과하는 문제

### 문제 상황

기존 이미지가 있는 성장 기록에서 새로 선택한 이미지 개수만 검사하면 최종 이미지 수가 최대 5장을 초과할 수 있었다.

예를 들어 기존 이미지가 4장인 기록에 새 이미지 3장을 추가하면 최종 이미지 수는 7장이 된다.

### 원인

다음 세 가지 수량을 함께 계산하지 않았기 때문이다.

```text
기존 이미지 수
삭제 예정 이미지 수
신규 이미지 수
```

신규 이미지 수만 확인하면 기존 이미지가 포함된 최종 저장 개수를 정확히 검증할 수 없다.

### 해결 방법

최종적으로 저장될 이미지 개수를 다음 공식으로 계산했다.

```text
최종 이미지 수
= 기존 이미지 수
- 삭제 예정 이미지 수
+ 신규 이미지 수
```

서버에서 최종 이미지 수가 5장을 초과하면 저장을 중단하도록 했다.

```java
if (
    existingImageCount
    - deletedImageCount
    + newImageCount
    > MAX_IMAGE_COUNT
) {
    throw new IllegalArgumentException(
        "기존 사진을 포함해 최대 "
            + MAX_IMAGE_COUNT
            + "장까지 등록할 수 있습니다."
    );
}
```

프론트엔드에서도 동일한 계산을 적용해 파일 선택 단계에서 사용자에게 안내했다.

```javascript
if (
    getRetainedImageCount() + files.length
    > maxCount
) {
    alert(
        `유지할 기존 사진과 새 사진은 최대 ${maxCount}장까지 등록할 수 있습니다.`
    );

    imageInput.value = "";
    return;
}
```

### 결과

프론트엔드와 서버에서 모두 최대 5장 제한을 검증해 이미지 개수 제한을 우회할 수 없도록 했다.

### 배운 점

* 수정 기능에서는 신규 데이터만이 아니라 기존 데이터와 삭제 예정 데이터까지 함께 계산해야 한다.
* 프론트엔드 검증은 사용자 편의를 위한 것이며 최종 검증은 서버에서 수행해야 한다.
* 동일한 제한 규칙을 프론트엔드와 서버에 일관되게 적용해야 한다.

## 6. 다른 성장 기록의 미디어가 삭제될 수 있는 문제

### 문제 상황

수정 요청에 포함된 미디어 번호만 사용해 삭제하면 요청값을 조작하여 다른 성장 기록의 미디어를 삭제할 가능성이 있었다.

### 원인

미디어 번호의 존재 여부만 확인하고 해당 미디어가 현재 수정 중인 성장 기록에 속하는지 검증하지 않았기 때문이다.

다음과 같은 요청 조작 가능성이 있었다.

```text
현재 수정 중인 기록 번호
→ 10

삭제 요청 미디어 번호
→ 실제로는 기록 번호 15에 속한 미디어
```

### 해결 방법

요청받은 모든 미디어가 현재 성장 기록에 속하는지 확인했다.

```java
boolean containsOtherRecordMedia =
        mediaToDelete.size()
                != requestedMediaNums.size()
        || mediaToDelete.stream()
                .anyMatch(media ->
                    !recordNum.equals(
                        media.getGrowthRecord()
                                .getRecordNum()
                    )
                );

if (containsOtherRecordMedia) {
    throw new IllegalArgumentException(
        "삭제할 수 없는 미디어가 포함되어 있습니다."
    );
}
```

다음 두 경우 모두 삭제 요청을 거부하도록 했다.

* 요청한 미디어 번호 중 존재하지 않는 값이 포함된 경우
* 다른 성장 기록에 속한 미디어가 포함된 경우

### 결과

존재하지 않는 미디어 번호나 다른 성장 기록의 미디어 번호가 포함되면 전체 삭제 요청이 거부되도록 보완했다.

### 배운 점

* 클라이언트에서 전달된 식별값은 신뢰해서는 안 된다.
* 하위 자원을 수정하거나 삭제할 때는 반드시 상위 자원과의 소유 관계를 검증해야 한다.
* 단순 존재 여부 검사만으로는 권한 검증이 충분하지 않다.

## 7. DB에서 미디어를 삭제해도 S3 파일이 남는 문제

### 문제 상황

DB에서 `Media` 엔티티를 삭제해도 S3에 실제 이미지 파일이 남아 고아 파일이 생성될 수 있었다.

### 원인

JPA의 `Cascade`와 `orphanRemoval`은 데이터베이스 엔티티 관계에만 적용된다.

외부 저장소인 S3 객체는 JPA가 자동으로 삭제할 수 없다.

```text
JPA Entity 삭제
→ DB 데이터만 삭제

S3 객체
→ 별도 삭제 필요
```

### 해결 방법

미디어가 이미지인 경우 DB 데이터를 삭제하기 전에 S3 객체를 먼저 삭제했다.

```java
for (Media media : mediaList) {
    if (
        media.getMediaType()
                == MediaType.IMAGE
        && media.getMediaUrl() != null
        && !media.getMediaUrl().isBlank()
    ) {
        s3FileStorageService.deleteImage(
            media.getMediaUrl()
        );
    }
}
```

S3 객체를 삭제한 후 DB의 미디어 데이터를 제거했다.

```java
mediaRepository.deleteAll(mediaList);
mediaRepository.flush();
```

성장 기록 전체를 삭제할 때도 연결된 미디어 정리 로직을 먼저 실행하도록 했다.

### 결과

미디어 또는 성장 기록 삭제 시 DB 데이터와 S3 객체가 함께 제거되어 고아 파일이 남지 않도록 개선했다.

### 배운 점

* JPA는 외부 저장소 파일까지 관리하지 않는다.
* DB 데이터와 외부 파일의 생명주기를 별도로 관리해야 한다.
* 파일 삭제와 DB 삭제 순서를 명확하게 설계해야 한다.
* 외부 저장소 삭제 실패 시 DB 삭제 처리 방식을 어떻게 할지도 추가로 고려해야 한다.

## 8. YouTube 썸네일 URL 생성 오류

### 문제 상황

생성된 YouTube 썸네일 이미지가 정상적으로 표시되지 않았다.

### 원인

YouTube 썸네일 URL에서 `vi`와 영상 ID 사이의 `/`가 빠져 있었다.

```java
return "https://img.youtube.com/vi"
        + youtubeVideoId
        + "/hqdefault.jpg";
```

잘못 생성된 주소는 다음과 같았다.

```text
https://img.youtube.com/viVIDEO_ID/hqdefault.jpg
```

### 해결 방법

`vi` 뒤에 `/`를 추가했다.

```java
return "https://img.youtube.com/vi/"
        + youtubeVideoId
        + "/hqdefault.jpg";
```

### 결과

다음과 같은 정상적인 YouTube 썸네일 주소가 생성되었다.

```text
https://img.youtube.com/vi/VIDEO_ID/hqdefault.jpg
```

### 배운 점

* 외부 서비스 URL은 문자열 연결 과정에서 `/` 누락 여부를 확인해야 한다.
* 생성된 URL은 로그나 브라우저 주소창에서 직접 확인하면 문제를 빠르게 찾을 수 있다.
* URL 생성 로직은 별도의 공통 메서드로 분리해 테스트하는 것이 좋다.

## 9. `updatedAt` 값이 수정 시 갱신되지 않는 문제

### 문제 상황

성장 기록이나 카테고리를 수정해도 `updatedAt` 값이 변경되지 않았다.

### 원인

`@UpdateTimestamp`가 적용된 필드에 `updatable = false`가 함께 설정되어 있었다.

```java
@UpdateTimestamp
@Column(
    name = "updated_at",
    nullable = false,
    updatable = false
)
private LocalDateTime updatedAt;
```

`updatable = false`는 JPA가 UPDATE SQL에 해당 컬럼을 포함하지 못하게 한다.

따라서 `@UpdateTimestamp`가 적용되어 있더라도 수정 시간 값이 DB에 반영되지 않는다.

또한 카테고리의 수정일 필드에는 `@CreationTimestamp`가 잘못 적용되어 있었다.

### 해결 방법

`updatable = false`를 제거하고 수정일 필드에 `@UpdateTimestamp`를 적용했다.

```java
@UpdateTimestamp
@Column(
    name = "updated_at",
    nullable = false
)
private LocalDateTime updatedAt;
```

생성일과 수정일의 어노테이션도 명확하게 구분했다.

```java
@CreationTimestamp
@Column(
    name = "created_at",
    nullable = false,
    updatable = false
)
private LocalDateTime createdAt;
```

```java
@UpdateTimestamp
@Column(
    name = "updated_at",
    nullable = false
)
private LocalDateTime updatedAt;
```

### 결과

엔티티가 수정될 때 `updatedAt` 값도 함께 갱신되도록 매핑을 수정했다.

### 배운 점

* 생성일에는 `@CreationTimestamp`를 사용한다.
* 수정일에는 `@UpdateTimestamp`를 사용한다.
* 생성일은 `updatable = false`로 설정할 수 있지만 수정일에는 적용하면 안 된다.
* JPA 컬럼 옵션과 Hibernate 자동 시간 어노테이션이 서로 충돌하지 않는지 확인해야 한다.

## 10. Lombok Builder 사용 시 미디어 목록이 `null`이 되는 문제

### 문제 상황

`GrowthRecord.builder()`로 엔티티를 생성하면 초기화해 둔 `mediaList`가 `null`이 될 가능성이 있었다.

```java
private List<Media> mediaList =
        new ArrayList<>();
```

### 원인

Lombok의 `@Builder`는 필드 선언부의 초기값을 자동으로 Builder의 기본값으로 사용하지 않는다.

Builder에서 해당 필드를 명시적으로 설정하지 않으면 초기화 표현식 대신 `null`이 들어갈 수 있다.

### 해결 방법

컬렉션 필드에 `@Builder.Default`를 추가했다.

```java
@Builder.Default
private List<Media> mediaList =
        new ArrayList<>();
```

연관관계 매핑과 함께 사용하면 다음과 같이 구성할 수 있다.

```java
@Builder.Default
@OneToMany(
    mappedBy = "growthRecord",
    cascade = CascadeType.ALL,
    orphanRemoval = true
)
private List<Media> mediaList =
        new ArrayList<>();
```

### 결과

Builder로 생성한 성장 기록에서도 미디어 컬렉션이 빈 리스트로 안전하게 초기화되었다.

### 배운 점

* Lombok Builder 사용 시 필드 초기값이 자동으로 유지되지 않을 수 있다.
* Builder에서 기본값이 필요한 필드에는 `@Builder.Default`를 사용해야 한다.
* JPA 컬렉션은 `null`보다 빈 컬렉션으로 초기화하는 것이 안전하다.

## 11. 테스트 실행 시 운영 DB와 외부 설정이 필요한 문제

### 문제 상황

Spring Context 테스트가 MySQL, AWS, 메일 등 운영 환경 설정에 의존해 로컬이나 CI 환경에서 실패할 가능성이 있었다.

### 원인

테스트가 기본 `application.yaml`을 그대로 사용하고 있었다.

운영 DB가 실행 중이지 않거나 AWS 환경변수가 설정되지 않으면 Spring Context 초기화에 실패할 수 있었다.

```text
MySQL 연결 실패
AWS Credentials 누락
메일 서버 설정 누락
외부 네트워크 의존
```

### 해결 방법

테스트 클래스에 테스트 전용 프로필을 적용했다.

```java
@SpringBootTest
@ActiveProfiles("test")
class GrowlogProjectApplicationTests {

}
```

H2 테스트 의존성을 추가하고 MySQL 호환 모드를 사용했다.

```yaml
spring:
  datasource:
    url: jdbc:h2:mem:growlog-test;MODE=MySQL;DB_CLOSE_DELAY=-1
    username: sa
    password:
    driver-class-name: org.h2.Driver

  jpa:
    hibernate:
      ddl-auto: create-drop

    open-in-view: false
```

테스트용 메일, AWS Region, S3 버킷 설정도 별도로 제공했다.

```yaml
spring:
  mail:
    host: localhost
    port: 2525
    username: test
    password: test

cloud:
  aws:
    region:
      static: ap-northeast-2

    s3:
      bucket: growlog-test-bucket
```

### 결과

운영 MySQL에 연결하지 않고 독립적인 인메모리 데이터베이스에서 Spring Context 테스트를 실행할 수 있는 기반을 마련했다.

### 배운 점

* 테스트는 운영 환경과 분리되어야 한다.
* `@ActiveProfiles("test")`를 사용하면 테스트 전용 설정을 적용할 수 있다.
* H2의 MySQL 호환 모드를 사용하면 일부 MySQL 문법 차이를 줄일 수 있다.
* 외부 서비스는 테스트에서 실제 호출하지 않도록 Mock 또는 Stub 적용도 고려해야 한다.

## 12. 이메일 발송 오류의 내부 정보가 사용자에게 노출되는 문제

### 문제 상황

이메일 인증번호 발송에 실패하면 예외 메시지가 사용자 응답에 그대로 포함되었다.

```java
"이메일 발송에 실패했습니다: "
        + e.getMessage()
```

### 원인

사용자에게 제공할 오류 메시지와 개발자가 확인할 상세 오류 로그를 분리하지 않았기 때문이다.

예외 메시지에는 다음과 같은 내부 정보가 포함될 수 있다.

```text
SMTP 서버 주소
인증 실패 원인
메일 계정 설정
네트워크 연결 정보
라이브러리 내부 메시지
```

### 해결 방법

상세 예외는 SLF4J 로그에 기록했다.

```java
log.error(
    "이메일 인증번호 발송에 실패했습니다. email={}",
    email,
    e
);
```

사용자에게는 일반화된 안내 메시지만 반환했다.

```java
return new EmailVerificationResponse(
    false,
    "이메일 발송에 실패했습니다. 잠시 후 다시 시도해 주세요."
);
```

### 결과

개발자는 서버 로그에서 상세한 원인을 확인할 수 있고, 사용자에게 내부 시스템 정보가 노출되는 것을 방지했다.

### 배운 점

* 사용자 메시지와 서버 로그는 목적이 다르다.
* 사용자에게는 이해하기 쉬운 일반 메시지를 제공해야 한다.
* 상세 예외와 Stack Trace는 서버 로그에 기록해야 한다.
* 이메일 주소와 같은 개인정보가 로그에 남을 때는 운영 환경의 로그 정책도 함께 고려해야 한다.

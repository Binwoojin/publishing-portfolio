# 2026-07-30 GrowLog 트러블슈팅

## 개요

2026년 7월 30일에는 GrowLog의 기존 세션 기반 로그인 구조를 Spring Security 기반 인증 구조로 전환하고, 실제 데이터를 이용한 월별 타임라인 기능을 구현했다.

이 과정에서 다음 영역의 문제를 해결했다.

* 기존 로그인 Controller와 Spring Security 인증 필터의 충돌
* Spring Security의 DB 회원 정보 조회
* 기존 세션 기반 Controller와 Security 인증 정보의 호환
* 반복되는 로그인 세션 검사 코드
* CSRF로 인한 `403 Forbidden`
* 로그인 실패 메시지 처리
* 로그아웃 시 인증 정보 제거
* 비밀번호 변경 검증 오류
* 목표와 성장 기록의 타임라인 통합
* 월별 데이터 조회 범위
* 잘못된 연도 및 월 파라미터 처리
* 환경 설정에 포함된 민감 정보
* 로컬, 운영, 테스트 환경 설정 분리

## 1. Spring Security 적용 후 기존 로그인 요청이 Controller와 충돌하는 문제

### 문제 상황

기존 프로젝트에서는 `HomeController`의 `POST /login` 메서드가 이메일과 비밀번호를 직접 확인하고 로그인 회원을 세션에 저장했다.

Spring Security를 적용한 후에는 같은 `/login` 요청을 Spring Security 인증 필터와 기존 Controller가 모두 처리하려는 구조가 되었다.

### 기존 로그인 처리 흐름

```text
POST /login
→ HomeController
→ MemberService.login()
→ 이메일과 비밀번호 확인
→ HttpSession에 loginMember 저장
```

### Spring Security 적용 후 필요한 처리 흐름

```text
POST /login
→ Spring Security 인증 필터
→ UserDetailsService
→ PasswordEncoder를 통한 비밀번호 검증
→ SecurityContext에 인증 정보 저장
```

### 원인

기존 세션 로그인 방식과 Spring Security 로그인 방식의 책임이 중복되었기 때문이다.

Spring Security에서 다음 설정을 적용하면 `POST /login` 요청은 인증 필터가 처리한다.

```java
.loginProcessingUrl("/login")
```

따라서 같은 요청을 처리하는 Controller 메서드를 함께 유지하면 로그인 처리 주체가 불명확해진다.

### 해결 방법

`HomeController`의 기존 `POST /login` 메서드를 제거하고 Spring Security가 로그인 요청을 처리하도록 변경했다.

```java
.formLogin(form -> form
        .loginPage("/login")
        .loginProcessingUrl("/login")
        .usernameParameter("email")
        .passwordParameter("password")
        .successHandler(loginSuccessHandler)
        .failureUrl("/login?error")
        .permitAll()
)
```

로그인 페이지를 표시하는 `GET /login` 요청만 Controller에 유지했다.

```java
@GetMapping("/login")
public String loginPage() {
    return "login";
}
```

### 결과

* 로그인 요청 처리 책임을 Spring Security로 일원화
* Controller와 Security 인증 필터의 요청 충돌 해결
* 직접 작성한 비밀번호 비교 로직 제거
* Spring Security의 인증 처리 구조 활용 가능

### 배운 점

* `loginProcessingUrl()`로 지정한 주소는 Spring Security 필터가 처리한다.
* 같은 URL과 HTTP Method를 Controller에서 중복 처리하지 않아야 한다.
* 로그인 화면 조회와 로그인 인증 처리는 서로 다른 책임이다.

## 2. Spring Security가 DB의 로그인 회원을 조회하지 못하는 문제

### 문제 상황

로그인 form의 요청은 Spring Security에 정상적으로 전달되었지만 프로젝트의 `Member` 데이터를 이용해 사용자를 인증할 수 없었다.

### 원인

Spring Security는 기본적으로 GrowLog의 `MemberRepository` 구조와 회원 조회 방식을 알지 못한다.

로그인 이메일을 이용해 회원을 조회하고, 조회 결과를 Spring Security가 이해할 수 있는 `UserDetails` 객체로 변환하는 코드가 필요했다.

### 해결 방법

`UserDetailsService`를 구현하는 `CustomUserDetailsService`를 추가했다.

```java
@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class CustomUserDetailsService
        implements UserDetailsService {

    private final MemberRepository memberRepository;

    @Override
    public UserDetails loadUserByUsername(
            String email
    ) throws UsernameNotFoundException {

        Member member = memberRepository
                .findByEmail(email)
                .orElseThrow(() ->
                        new UsernameNotFoundException(
                                "회원 정보를 찾을 수 없습니다."
                        )
                );

        return new LoginMemberPrincipal(member);
    }
}
```

Spring Security 인증에 필요한 회원 정보를 제공하기 위해 `LoginMemberPrincipal`도 구현했다.

```java
@Getter
public class LoginMemberPrincipal
        implements UserDetails {

    private final Long memberNo;
    private final String email;
    private final String password;
    private final String nickname;

    public LoginMemberPrincipal(Member member) {
        this.memberNo = member.getMemberNo();
        this.email = member.getEmail();
        this.password = member.getPassword();
        this.nickname = member.getNickname();
    }

    @Override
    public String getUsername() {
        return email;
    }
}
```

### 인증 처리 흐름

```text
로그인 form에서 이메일과 비밀번호 전송
→ Spring Security가 CustomUserDetailsService 호출
→ 이메일로 Member 조회
→ Member를 LoginMemberPrincipal로 변환
→ PasswordEncoder로 비밀번호 비교
→ 인증 성공 시 SecurityContext 저장
```

### 결과

* Spring Security에서 이메일 기반 회원 조회 가능
* DB에 저장된 BCrypt 비밀번호로 로그인 인증 가능
* 회원 번호와 닉네임을 인증 객체에서 활용 가능
* `Member` Entity와 인증 객체의 책임 분리

### 배운 점

* Spring Security에서 DB 회원을 인증하려면 `UserDetailsService` 구현이 필요하다.
* `loadUserByUsername()`의 username은 반드시 일반 아이디일 필요가 없으며 이메일을 사용할 수 있다.
* JPA Entity를 Security 인증 객체로 직접 사용하기보다 별도의 Principal 객체를 두는 것이 안전하다.

## 3. Spring Security 로그인 성공 후 기존 Controller가 비로그인 상태로 판단하는 문제

### 문제 상황

Spring Security 인증에는 성공했지만 일부 기존 Controller에서는 사용자를 로그인하지 않은 상태로 판단했다.

### 원인

Spring Security는 인증 정보를 다음 구조에 저장한다.

```text
SecurityContext
└── Authentication
    └── Principal
```

하지만 기존 Controller는 다음과 같이 HTTP 세션의 `loginMember` 속성을 직접 조회하고 있었다.

```java
Member loginMember =
        (Member) session.getAttribute(
                "loginMember"
        );
```

Security Context에 인증 정보가 존재해도 세션에 `loginMember`가 없다면 기존 Controller는 비로그인 상태로 판단한다.

### 해결 방법

로그인 성공 직후 실행되는 `LoginSuccessHandler`를 추가했다.

```java
@Component
@RequiredArgsConstructor
public class LoginSuccessHandler
        implements AuthenticationSuccessHandler {

    private final MemberService memberService;

    @Override
    public void onAuthenticationSuccess(
            HttpServletRequest request,
            HttpServletResponse response,
            Authentication authentication
    ) throws IOException {

        LoginMemberPrincipal principal =
                (LoginMemberPrincipal)
                        authentication.getPrincipal();

        Member loginMember =
                memberService.findById(
                        principal.getMemberNo()
                );

        request.getSession()
                .setAttribute(
                        "loginMember",
                        loginMember
                );

        response.sendRedirect(
                request.getContextPath()
                        + "/home"
        );
    }
}
```

### 결과

* Spring Security 인증 정보가 `SecurityContext`에 저장
* 기존 Controller와의 호환을 위해 `loginMember`를 세션에도 임시 저장
* 인증 방식 전환 중에도 기존 기능 정상 유지
* Controller를 단계적으로 Principal 기반으로 변경 가능

> 이 방식은 Spring Security 마이그레이션을 위한 임시 처리이다. 모든 Controller가 `@AuthenticationPrincipal` 방식으로 전환되면 세션 저장 로직을 제거할 예정이다.

### 배운 점

* Spring Security 인증 정보와 직접 저장한 세션 속성은 서로 다른 데이터다.
* 인증 구조를 단계적으로 변경할 때는 임시 호환 계층을 사용할 수 있다.
* 임시 호환 코드는 제거 조건과 시점을 명확하게 정해야 한다.

## 4. Controller마다 로그인 세션 검사 코드가 반복되는 문제

### 문제 상황

목표와 성장 기록 Controller의 거의 모든 메서드에서 로그인 회원을 세션에서 꺼내고 `null`을 검사하는 코드가 반복되었다.

```java
Member loginMember =
        (Member) session.getAttribute(
                "loginMember"
        );

if (loginMember == null) {
    return "redirect:/login";
}
```

### 원인

인증 여부 확인과 로그인 페이지 이동을 각 Controller가 직접 담당하고 있었기 때문이다.

이 구조에서는 다음 문제가 발생한다.

* 동일한 로그인 검사 코드 반복
* 일부 메서드에서 인증 검사가 누락될 가능성
* Controller가 인증과 비즈니스 요청을 동시에 처리
* Spring Security 인증 정보를 활용하지 못함

### 해결 방법

보호가 필요한 URL을 `SecurityConfig`에 등록했다.

```java
.requestMatchers(
        "/goal/**",
        "/record/**",
        "/home",
        "/timeline",
        "/mypage/**"
)
.authenticated()
```

Controller에서는 `@AuthenticationPrincipal`을 이용해 인증된 회원 정보를 전달받도록 변경했다.

```java
@GetMapping("/list")
public String goalList(
        @AuthenticationPrincipal
        LoginMemberPrincipal principal,
        Model model
) {
    List<Goal> goals =
            goalService.findGoalsByMember(
                    principal.getMemberNo()
            );

    model.addAttribute(
            "goal",
            goals
    );

    return "goal/list";
}
```

### 결과

* 인증되지 않은 요청은 Controller 실행 전에 차단
* 반복적인 세션 검사 코드 제거
* 로그인 회원 번호를 Principal에서 일관되게 조회
* 인증 처리와 비즈니스 요청 처리의 책임 분리
* 인증 검사 누락 가능성 감소

### 배운 점

* 접근 제한은 개별 Controller보다 Security 설정에서 중앙 관리하는 것이 적절하다.
* Controller는 인증 여부를 검사하기보다 인증된 사용자의 정보를 받아 비즈니스 로직을 처리해야 한다.
* 보호할 URL 목록이 추가될 때 Security 설정도 함께 점검해야 한다.

## 5. Spring Security 적용 후 POST 요청이 `403 Forbidden`으로 실패하는 문제

### 문제 상황

Spring Security를 적용한 뒤 로그인, 로그아웃, 회원가입, 목표 등록 등 상태를 변경하는 POST 요청이 `403 Forbidden`으로 실패할 수 있었다.

```text
HTTP 403 Forbidden
```

### 원인

Spring Security는 상태 변경 요청에 CSRF 보호를 기본 적용한다.

하지만 기존 JSP form에는 CSRF 토큰이 포함되어 있지 않았다.

```text
POST 요청
→ Spring Security CSRF 검사
→ 요청에 CSRF 토큰 없음
→ 403 Forbidden
```

### 임시 해결 방법

기존 기능이 정상적으로 동작하는지 먼저 확인하기 위해 CSRF 검사를 임시로 비활성화했다.

```java
.csrf(csrf -> csrf.disable());
```

일부 form에는 향후 CSRF 활성화를 고려해 토큰 필드를 추가하기 시작했다.

```jsp
<input
    type="hidden"
    name="${_csrf.parameterName}"
    value="${_csrf.token}"
>
```

### 결과

* Spring Security 적용 직후 모든 기존 POST 요청이 차단되는 문제 방지
* 기존 작성, 수정, 삭제 기능 테스트 가능
* CSRF 토큰 적용을 위한 후속 작업 확인

### 후속 조치

CSRF 비활성화는 최종 해결 방법이 아니다.

모든 상태 변경 form에 다음 토큰을 추가한 뒤 CSRF 보호를 다시 활성화해야 한다.

```jsp
<input
    type="hidden"
    name="${_csrf.parameterName}"
    value="${_csrf.token}"
>
```

적용 대상은 다음과 같다.

* 로그인 form
* 로그아웃 form
* 회원가입 form
* 목표 등록, 수정, 삭제 form
* 성장 기록 등록, 수정, 삭제 form
* 계정 설정 form
* 이메일 인증 관련 form

### 배운 점

* Spring Security 도입 후 POST 요청이 `403`이면 CSRF 토큰을 먼저 확인해야 한다.
* 기능 확인을 위한 임시 비활성화와 운영 환경의 최종 설정을 구분해야 한다.
* GET 요청으로 데이터를 변경하지 말고 POST, PUT, DELETE 요청에 CSRF 보호를 적용해야 한다.

## 6. 로그인 실패 원인이 사용자에게 일관되게 표시되지 않는 문제

### 문제 상황

기존 로그인 실패 메시지는 Controller의 `RedirectAttributes`를 통해 전달했다.

Spring Security가 로그인을 처리하도록 변경한 후에는 기존 `loginErrorMessage`가 전달되지 않았다.

### 원인

기존 로그인 실패 흐름과 Spring Security의 인증 실패 흐름이 서로 달랐다.

### 기존 흐름

```text
Controller에서 로그인 실패
→ Flash Attribute 저장
→ /login으로 리다이렉트
→ JSP에서 오류 메시지 출력
```

### Spring Security 흐름

```text
인증 필터에서 로그인 실패
→ failureUrl로 리다이렉트
→ /login?error
```

### 해결 방법

인증 실패 주소를 `/login?error`로 설정했다.

```java
.failureUrl("/login?error")
```

JSP에서는 `error` 파라미터의 존재 여부를 확인해 메시지를 제공했다.

```jsp
<input
    type="hidden"
    id="loginErrorMessage"
    value="${param.error != null
        ? '이메일 또는 비밀번호가 올바르지 않습니다.'
        : ''}"
>
```

### 결과

* Spring Security 인증 실패 시 기존 로그인 화면에서 오류 메시지 표시
* 로그인 실패 메시지 처리 방식 일원화
* 이메일 존재 여부와 비밀번호 오류를 구분하지 않아 계정 정보 추측 가능성 감소

### 배운 점

* 인증 처리 주체가 변경되면 실패 메시지 전달 방식도 함께 변경해야 한다.
* 로그인 실패 시 이메일 존재 여부와 비밀번호 오류를 구체적으로 구분하지 않는 것이 보안상 안전하다.
* 쿼리 파라미터를 이용한 메시지는 사용자 입력값을 직접 출력하지 않도록 주의해야 한다.

## 7. 로그아웃 후 인증 정보가 완전히 제거되지 않을 수 있는 문제

### 문제 상황

기존 로그아웃은 Controller에서 HTTP 세션만 무효화했다.

```java
session.invalidate();
```

Spring Security 적용 후에는 HTTP 세션뿐만 아니라 `SecurityContext`의 인증 정보도 함께 제거해야 한다.

### 원인

기존 로그아웃 로직이 Spring Security의 인증 상태를 고려하지 않았기 때문이다.

세션만 무효화하고 Security Context를 명확하게 정리하지 않으면 인증 처리 구조가 불완전해질 수 있다.

### 해결 방법

로그아웃 처리를 Spring Security에 위임했다.

```java
.logout(logout -> logout
        .logoutUrl("/logout")
        .logoutSuccessUrl("/logout-complete")
        .invalidateHttpSession(true)
        .clearAuthentication(true)
        .permitAll()
)
```

기존 `HomeController`의 `POST /logout` 메서드는 제거하고 로그아웃 완료 화면만 유지했다.

```java
@GetMapping("/logout-complete")
public String logoutCompletePage() {
    return "logout";
}
```

### 결과

로그아웃 시 다음 정보가 함께 제거되도록 수정했다.

* 기존 HTTP 세션
* 세션에 임시 저장한 `loginMember`
* Spring Security `Authentication`
* `SecurityContext`의 인증 정보

### 배운 점

* Spring Security를 사용하는 프로젝트에서는 로그인뿐 아니라 로그아웃도 Security에 위임하는 것이 적절하다.
* 세션 무효화와 인증 정보 제거는 관련 있지만 동일한 처리가 아니다.
* CSRF를 활성화하면 로그아웃 요청도 CSRF 토큰을 포함한 POST 방식으로 처리해야 한다.

## 8. 비밀번호 변경 시 현재 비밀번호 검증이 실패하는 문제

### 문제 상황

사용자가 올바른 현재 비밀번호를 입력해도 비밀번호 변경 검증이 정상적으로 처리되지 않을 수 있었다.

### 원인

현재 비밀번호를 저장해야 하는 변수에 신규 비밀번호를 대입하고 있었다.

### 수정 전

```java
String currentPassword =
        request.getCurrentPassword() == null
                ? ""
                : request.getNewPassword();
```

`getCurrentPassword()`가 `null`이 아닐 때 `getNewPassword()`를 사용하고 있어 현재 비밀번호 검증에 잘못된 값이 전달되었다.

### 해결 방법

사용자가 입력한 현재 비밀번호를 올바르게 사용하도록 수정했다.

```java
String currentPassword =
        request.getCurrentPassword() == null
                ? ""
                : request.getCurrentPassword();
```

이후 저장된 암호화 비밀번호와 비교하도록 처리했다.

```java
passwordEncoder.matches(
        currentPassword,
        member.getPassword()
);
```

### 결과

* 사용자가 입력한 현재 비밀번호를 정상적으로 검증
* DB에 저장된 BCrypt 비밀번호와 올바르게 비교
* 정상 입력인데도 비밀번호 변경이 실패하는 문제 해결

### 배운 점

* 이름이 비슷한 DTO getter를 사용할 때 잘못된 값을 대입하지 않았는지 확인해야 한다.
* 비밀번호 관련 로직은 값의 출처를 단계별로 명확하게 구분해야 한다.
* 현재 비밀번호는 `matches()`, 새 비밀번호는 `encode()`에 사용해야 한다.

## 9. 타임라인에서 목표와 성장 기록을 하나의 목록으로 처리하기 어려운 문제

### 문제 상황

타임라인에는 목표와 성장 기록을 생성 시간 순서대로 함께 표시해야 했다.

하지만 `Goal`과 `GrowthRecord`는 서로 다른 Entity이며 필드명과 상세 이동 주소도 달랐다.

### 원인

두 Entity의 목록을 JSP에서 직접 분기하며 출력하면 다음 문제가 발생한다.

* 화면 코드의 조건문 증가
* 서로 다른 두 목록을 전체 시간순으로 정렬하기 어려움
* Entity 구조가 JSP에 강하게 노출
* 필터 기능 구현 복잡
* 공통 카드 UI 중복

### 해결 방법

화면 출력에 필요한 공통 필드를 가진 `TimelineItem` DTO를 추가했다.

```java
@Getter
@AllArgsConstructor
public class TimelineItem {

    private String type;
    private Long itemNum;
    private String title;
    private String content;
    private LocalDateTime createdAt;
    private String detailUrl;
}
```

`TimelineService`에서 목표와 성장 기록을 각각 `TimelineItem`으로 변환한 뒤 하나의 목록에 저장했다.

```java
timelineItems.sort(
        Comparator.comparing(
                TimelineItem::getCreatedAt
        ).reversed()
);
```

### 변환 구조

```text
Goal
→ TimelineItem(type = GOAL)

GrowthRecord
→ TimelineItem(type = RECORD)

두 목록 병합
→ createdAt 기준 최신순 정렬
→ JSP 전달
```

### 결과

* 목표와 성장 기록을 하나의 리스트로 관리
* 생성 시간 기준 최신순 통합 정렬
* JSP에서 공통 카드 구조 사용 가능
* `type` 값을 이용한 필터 구현 가능
* Entity와 화면 모델의 책임 분리

### 배운 점

* 서로 다른 Entity를 하나의 화면에서 출력할 때 반드시 상속 구조로 변경할 필요는 없다.
* 화면에 필요한 공통 구조는 전용 DTO로 정의할 수 있다.
* Entity를 JSP에 직접 노출하는 것보다 화면 전용 모델을 사용하는 것이 유지보수에 유리하다.

## 10. 타임라인에서 월별 데이터만 정확히 조회하기 어려운 문제

### 문제 상황

선택한 연도와 월에 해당하는 목표 및 성장 기록만 조회해야 했다.

월의 마지막 날짜를 직접 계산하거나 날짜만 비교하면 시간 정보가 포함된 `createdAt` 데이터가 누락될 가능성이 있었다.

### 문제가 될 수 있는 조회 범위

```text
2026-07-01 00:00:00 이상
2026-07-31 23:59:59 이하
```

DB의 시간 정밀도가 밀리초 또는 나노초 단위인 경우 다음과 같은 데이터가 누락될 수 있다.

```text
2026-07-31 23:59:59.500
2026-07-31 23:59:59.999999
```

### 원인

월말의 마지막 시간을 직접 만들어 `이하` 조건으로 비교하려 했기 때문이다.

날짜별 마지막 시간을 직접 계산하는 방식은 DB 정밀도와 시간 타입에 따라 경계 오류를 만들 수 있다.

### 해결 방법

조회 범위를 시작 시각 이상, 다음 달 시작 시각 미만으로 설정했다.

```text
2026-07-01 00:00:00 이상
2026-08-01 00:00:00 미만
```

Repository 메서드는 다음 조건을 사용했다.

```java
findByMemberMemberNoAndCreatedAtGreaterThanEqualAndCreatedAtLessThanOrderByCreatedAtDesc(
        memberNo,
        startDateTime,
        endDateTime
);
```

조회 조건을 수식으로 표현하면 다음과 같다.

```text
startDateTime <= createdAt
&&
createdAt < endDateTime
```

### 결과

* 월의 마지막 날짜를 직접 계산할 필요가 없어짐
* 시간 정밀도에 따른 월말 데이터 누락 방지
* 윤년 및 월별 날짜 수 차이를 `YearMonth`가 자동 처리
* 회원 번호 조건을 포함해 다른 사용자의 데이터 제외

### 배운 점

* 기간 조회에는 반개구간 방식이 안전하다.
* 종료 시각을 해당 기간의 마지막 순간이 아니라 다음 기간의 시작 시각으로 계산할 수 있다.
* 월별 데이터 조회 시 회원 식별 조건도 반드시 함께 사용해야 한다.

## 11. 잘못된 연도 및 월 파라미터로 타임라인 요청이 실패하는 문제

### 문제 상황

다음과 같이 올바르지 않은 월이 전달되면 `YearMonth.of()`에서 예외가 발생할 수 있었다.

```text
/timeline?year=2026&month=13
```

또한 현재보다 미래인 월을 요청하면 아직 존재하지 않는 기간으로 이동할 수 있었다.

### 원인

사용자가 전달한 쿼리 파라미터를 검증하지 않고 바로 `YearMonth`로 변환했기 때문이다.

브라우저 화면에서 선택할 수 없는 값이어도 주소를 직접 변경하면 잘못된 값이 전달될 수 있다.

### 해결 방법

연도와 월의 변환 과정에서 예외가 발생하면 현재 월을 사용하도록 처리했다.

```java
try {
    selectedMonth =
            year != null
            && month != null
                    ? YearMonth.of(
                            year,
                            month
                    )
                    : currentMonth;

} catch (RuntimeException e) {
    selectedMonth = currentMonth;
}
```

현재보다 미래인 월도 현재 월로 제한했다.

```java
if (selectedMonth.isAfter(currentMonth)) {
    selectedMonth = currentMonth;
}
```

### 결과

* 연도 및 월 파라미터가 없으면 현재 월 조회
* 잘못된 월 값이 들어와도 페이지 오류 방지
* 미래 월 접근 제한
* 타임라인 페이지가 항상 유효한 조회 월 사용

### 배운 점

* 쿼리 파라미터는 사용자가 직접 조작할 수 있으므로 서버 검증이 필요하다.
* 날짜 객체 생성 과정에서도 예외 처리가 필요하다.
* 잘못된 입력값에 대해 오류 화면을 보여줄지 기본값으로 대체할지 서비스 정책을 정해야 한다.

## 12. 소스 코드에 DB 및 메일 계정 정보가 노출되는 문제

### 문제 상황

기본 설정 파일에 데이터베이스 주소, 사용자명, 비밀번호 및 메일 계정 정보가 직접 작성되어 있었다.

```yaml
spring:
  datasource:
    url: 실제_DB_주소
    username: 실제_사용자명
    password: 실제_비밀번호

  mail:
    username: 실제_메일_주소
    password: 실제_앱_비밀번호
```

### 원인

개발 초기 설정을 환경별로 분리하지 않고 `application.yaml`에 직접 작성했기 때문이다.

해당 파일을 GitHub에 업로드하면 민감 정보가 저장소와 Git 이력에 남을 수 있다.

### 해결 방법

민감한 설정값을 환경변수로 변경했다.

```yaml
spring:
  datasource:
    url: ${DB_URL}
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}

  mail:
    username: ${MAIL_USERNAME}
    password: ${MAIL_PASSWORD}
```

AWS 설정도 환경변수를 사용하도록 정리했다.

```yaml
cloud:
  aws:
    credentials:
      access-key: ${AWS_ACCESS_KEY:${AWS_ACCESS_KEY_ID:}}
      secret-key: ${AWS_SECRET_KEY:${AWS_SECRET_ACCESS_KEY:}}
```

### 결과

* 소스 코드에서 DB 자격 증명 제거
* 메일 계정과 앱 비밀번호 제거
* 실행 환경에서 민감 정보 주입 가능
* 로컬 및 운영 환경에서 서로 다른 값 사용 가능

### 추가 조치

과거 Git 커밋에 실제 자격 증명이 포함되었다면 현재 파일에서 삭제하는 것만으로는 충분하지 않다.

다음 조치가 필요하다.

* 노출된 DB 비밀번호 변경
* 메일 앱 비밀번호 폐기 및 재발급
* AWS 키가 노출되었다면 기존 키 비활성화
* 필요할 경우 Git 기록에서 민감 정보 제거
* `.env`와 IDE 실행 설정 파일이 Git에 포함되지 않도록 확인

### 배운 점

* Git에 한 번 올라간 정보는 현재 파일에서 삭제해도 이전 커밋에 남을 수 있다.
* 비밀번호와 Access Key는 노출 가능성이 확인되면 반드시 교체해야 한다.
* 환경변수 이름만 저장소에 기록하고 실제 값은 실행 환경에서 관리해야 한다.

## 13. 로컬과 운영 환경이 동일한 JPA 설정을 사용하는 문제

### 문제 상황

로컬 개발 환경과 운영 환경이 동일한 `ddl-auto`와 SQL 로그 설정을 사용하면 운영 DB가 의도하지 않게 변경되거나 상세 SQL이 운영 로그에 노출될 수 있었다.

### 원인

환경별 설정 파일과 Spring Profile이 분리되어 있지 않았기 때문이다.

### 해결 방법

로컬과 운영 프로필을 분리했다.

### 로컬 환경 설정

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: update

    show-sql: true
```

로컬에서는 다음 목적을 가진다.

* Entity 변경을 개발 DB에 빠르게 반영
* 실행 SQL 확인
* 개발 편의성 우선

### 운영 환경 설정

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate

    show-sql: false
```

운영에서는 다음 목적을 가진다.

* 운영 스키마 자동 변경 방지
* Entity와 DB 구조 일치 여부만 검사
* 상세 SQL 출력 제한

세션 쿠키도 HTTPS 환경에서만 전송하도록 설정했다.

```yaml
server:
  servlet:
    session:
      cookie:
        secure: true
```

### 결과

* 로컬 개발 편의성 유지
* 운영 DB 자동 변경 방지
* 운영 SQL 상세 로그 제한
* HTTPS 환경에서 세션 쿠키 보안 강화

### 배운 점

* `ddl-auto: update`는 운영 환경에서 예기치 않은 스키마 변경을 만들 수 있다.
* 운영 환경에서는 `validate` 또는 마이그레이션 도구 사용을 고려해야 한다.
* 환경별 설정 차이는 Profile 파일에서 명시적으로 관리하는 것이 좋다.

## 14. 테스트가 운영 DB와 외부 서비스 설정에 의존하는 문제

### 문제 상황

Spring Context 테스트가 기본 설정을 사용하면 운영 MySQL, 메일 계정, AWS 설정이 없는 환경에서 테스트가 실패할 수 있었다.

### 원인

테스트 전용 Profile과 데이터베이스가 분리되어 있지 않았기 때문이다.

테스트 실행이 다음 외부 환경에 의존하고 있었다.

```text
운영 또는 개발 MySQL
메일 서버 설정
AWS Access Key
S3 버킷 설정
외부 네트워크
```

### 해결 방법

테스트 클래스에 `test` Profile을 적용했다.

```java
@SpringBootTest
@ActiveProfiles("test")
class GrowlogProjectApplicationTests {

}
```

테스트 의존성으로 H2를 추가했다.

```xml
<dependency>
    <groupId>com.h2database</groupId>
    <artifactId>h2</artifactId>
    <scope>test</scope>
</dependency>
```

테스트에서는 MySQL 호환 모드의 인메모리 DB를 사용하도록 구성했다.

```yaml
spring:
  datasource:
    url: jdbc:h2:mem:growlog-test;MODE=MySQL;DB_CLOSE_DELAY=-1
    username: sa
    password:
    driver-class-name: org.h2.Driver

  jpa:
    hibernate:
      ddl-auto: create-drop
```

### 결과

* 운영 MySQL에 연결하지 않고 테스트 실행 가능
* 테스트 실행 시마다 독립적인 DB 생성
* 테스트 종료 후 DB 데이터 제거
* 로컬 및 CI 환경에서 테스트 실행 기반 마련

### 배운 점

* 테스트는 운영 환경과 독립적으로 실행되어야 한다.
* H2 MySQL 호환 모드로 일부 문법 차이를 줄일 수 있지만 완전한 MySQL 대체는 아니다.
* AWS와 메일 같은 외부 서비스는 테스트에서 Mock 또는 Stub으로 대체하는 것이 좋다.
* Context 로딩 테스트와 실제 기능 테스트를 구분해야 한다.

# 오늘의 트러블슈팅 요약

오늘 발생한 문제는 크게 세 영역으로 구분할 수 있었다.

## 1. 기존 세션 인증과 Spring Security 인증의 충돌

```text
기존 Controller 로그인 처리 제거
→ CustomUserDetailsService 구현
→ LoginMemberPrincipal 구현
→ LoginSuccessHandler로 임시 세션 호환
→ Controller를 @AuthenticationPrincipal 방식으로 전환
```

Spring Security 도입 과정에서는 모든 인증 코드를 한 번에 교체하지 않고 성공 Handler를 이용한 임시 호환 계층을 구성했다.

이를 통해 기존 기능을 유지하면서 Controller를 순차적으로 Principal 기반 방식으로 변경할 수 있었다.

---

## 2. 서로 다른 도메인 데이터를 타임라인으로 통합

```text
Goal 조회
→ TimelineItem 변환

GrowthRecord 조회
→ TimelineItem 변환

두 목록 병합
→ createdAt 기준 최신순 정렬
→ JSP 전달
```

타임라인은 목표와 성장 기록을 화면 전용 DTO로 변환해 Entity 구조를 변경하지 않고 통합했다.

월별 조회에는 시작 시각 이상, 다음 달 시작 시각 미만 조건을 사용해 월말 데이터 누락 가능성을 줄였다.

---

## 3. 로컬, 운영, 테스트 환경 설정 분리

```text
공통 설정
→ 환경변수 사용

local Profile
→ 개발 편의성 중심

prod Profile
→ 운영 안정성과 보안 중심

test Profile
→ H2 기반 독립 테스트
```

환경 설정은 Profile과 환경변수를 기반으로 분리했다.

소스 코드에 직접 작성된 DB, 메일, AWS 정보를 제거하고 실행 환경에서 주입하도록 변경했다.
